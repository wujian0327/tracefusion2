# Java 完整入口快照重放控制组

本轮在原有 7 个受控场景上比较 full、sparse、boundary，三组统一使用 **snapshot-v2**。结论是：在当前受限字节码、完整声明入口状态和无隐藏外部修改契约下，**边界快照已经足够恢复全部指定来源；内部观测不是这些查询的必要条件**。局部覆盖写入、循环、嵌套静态调用也可重放，不要求业务对象始终只读。

这是自实现控制组，不是 MirrorTaint、FlowDist 或 HardTaint 的复现；没有新增真实 Java 应用或业务函数。与此前 v1 两组实验的快照成本不同，不能直接把旧性能数字拼进本轮表格。

## 观测与还原

| 方法 | 实际运行时证据 |
| --- | --- |
| full | 根入口完整字段快照；逐条 step；字段、分支、调用、返回 |
| sparse | 同样的根入口快照；字段、分支、调用、返回，无 step |
| boundary | 根入口参数和对象身份；完整声明字段快照；根返回值及完成状态 |

根入口由用户显式指定，仍以静态调用闭包绑定范围。snapshot-v2 根据根参数声明类型，采集其**全部声明的非 static int 字段**；要求字段 public、非 volatile、可访问。非 int 字段不属于当前指令模型；数组、对象分配、引用字段加载、外部调用等仍拒绝。各字段记录包含参数槽、对象 ID、声明字段和值；别名保留同一对象身份并核对快照一致性。此处“完整”是模型内可访问状态完整，不是整个 JVM 堆快照。

每次根调用都承担相同快照成本。原始 class、字段声明 class、查询、入口及快照布局均绑定摘要。入口递归不支持；范围内其余调用和指令执行仍有数量/深度上限。初始来源仍定义在第一根调用范围开始时，后续快照只核对已有状态，不把已写字段重新标记为初始来源。

boundary 只给入口方法插入入口、快照和返回记录，辅助方法不插桩。返回事件只记录方法名和值，**不携带返回指令位置**，避免由不同 return 位置泄露选择分支。原始日志也不含内部字段访问、分支方向、调用、step。对嵌套场景的插桩后 class 做了 javap 检查：`choose`、`twice` 保持无 Recorder 调用，`nested` 仅含根边界与快照记录。

`boundary.py` 读取原始字节码及这些边界记录，在完整初态上执行局部变量、操作数栈、分支、内存版本及嵌套调用。它复用 `Engine.step/observe` 的操作数依赖语义，**不读取 full/sparse 的运行日志、选择结果或夹具答案**。这是共享语义引擎、不同证据输入的控制组，不能称为完全独立实现的语义验证器。独立夹具真值由外部评分器核对。

兼容输出中的 `branch_observations` 在 boundary 模式下是**重放得到的条件信息**，不是实际采集的分支证据；以 `observation.mode=boundary` 区分。其 `derived_steps` 同样是计算量，不可计入原始事件数。模型不支持、快照不完整或返回不一致时返回 unknown。

范围内无未建模外部修改仍由契约约束。采集器不能证明整个 JVM 没有其他线程、反射或 native 改写对象。字段写入可能被后续快照核对，但没有出口堆快照就不能声称核验了全部最终堆状态。本轮只回答声明的根返回来源。

## 运行

Linux、JDK 17+、Python 3.10+、`cc`。默认 200 次原有 sum 调用、1 个准备块、6 个正式配对块；每块 native/full/sparse/boundary 的顺序随机并保存。

```bash
git switch perf/payment-steady-state
git pull --ff-only origin perf/payment-steady-state
python3 experiments/java-collection/compare_observations.py --with-boundary
# 有多个 JDK 时添加 --jdk /path/to/jdk
```

不带 `--with-boundary` 仍运行旧 v1 两组实验。单独生成 v2 配置时，给 `observation.py` 增加 `--snapshots`；采集参数用 `-Dtracefusion.mode=boundary`，还原入口仍为 `infer.py`。

已有原始记录只需离线复核：

```bash
python3 experiments/java-collection/verify_observations.py \
  artifacts/java-observation-YYYYMMDD-HHMMSS-xxxxxx \
  --output artifacts/java-boundary-verification-new
```

## 本地结果：2026-10-10

实际 Corretto 17.0.20.1+12-LTS JVM，采集目录 `java-observation-20261010-093820-220882`。default 与 `-Xint` 各运行 7 个原有场景；三组共 **42 份正常采集**。各组 16 个根返回查询，不是 48 个独立业务场景。

| 指标 | full | sparse | boundary |
| --- | ---: | ---: | ---: |
| 正确来源查询 | 16/16 | 16/16 | 16/16 |
| 原始事件 | 342 | 168 | 106 |
| 原始 step | 174 | 0 | 0 |
| 还原的 step | 0 | 174 | 174 |

三组完整依赖图、来源答案、别名关系及条件操作数来源逐项一致。边界组相对 sparse 少 **36.90%** 原始事件，相对 full 少 **69.01%**。原始事件包含 start/class/finish 等固定成本，不能与下方重复负载的事件降幅混用。

边界组 **14 项离线故障**均 unknown：快照/入口/返回/完成行缺失、重复快照、对象错误、值与返回不符、插入内部事件、别名不一致、后续快照状态不符、查询/计划/scope 改变。另有 **2 次实际 JVM 拒绝场景**（null、第二应用线程），业务输出保持预期，采集与推断均拒绝。

另做一项正向敏感性检查：将选择参数从右改为左，保持两个对象值和返回值同为 17，还原来源随之从 `right.value` 改为 `left.value`。这是与模型一致的另一份执行证据，应给出不同来源，不能错误要求它返回 unknown。哈希及内部一致性检查不构成主机真实性证明。

原有 sparse 的 12 项检查和复核新增的 6 项写入/调用故障继续通过。归档复核检查 **1,010 个文件摘要**，重新推断全部正常记录和成本记录，复算事件数、日志大小及配对统计。边界组两个额外实际 JVM 拒绝记录单独归档，不计入上述 1,010 个原采集文件。

## 完整命令成本

三组均为相同原始 `Subject.sum`、相同输入和 200 次调用。无插桩基线保留；每次检查总输出与第一、最后根返回的来源。构建和离线入口规划不计入以下数字；在线包含 JVM 启动、类加载、ASM 变换、采集和日志写出；离线包含 Python 启动、证据核对、重放、依赖图和完整结果写出。内嵌 Agent 的在线 CPU 无法拆成独立业务/采集进程 CPU。

| 6 次正式运行中位数 | native | full | sparse | boundary |
| --- | ---: | ---: | ---: | ---: |
| 在线完整命令耗时 | 65.97 ms | 272.73 ms | 240.62 ms | 221.84 ms |
| 离线完整命令耗时 | — | 185.68 ms | 171.47 ms | 156.31 ms |
| 在线＋离线耗时 | 65.97 ms | 452.93 ms | 412.09 ms | 376.59 ms |
| 在线＋离线 CPU | 74.60 ms | 689.55 ms | 546.65 ms | 497.30 ms |
| 原始事件 | 0 | 10,403 | 2,403 | 803 |
| 原始日志字节 | 0 | 1,245,508 | 318,026 | 106,688 |

总和的中位数独立按每次实际合计计算，不要求等于各列中位数相加。下面是逐块配对降幅中位数，不是组中位数相除：

| boundary 相对基线 | full | sparse |
| --- | ---: | ---: |
| 原始事件减少 | 92.28% | 66.58% |
| 在线耗时降低 | 19.91% | 5.71% |
| 在线＋离线耗时降低 | 17.57% | 7.90% |
| 在线＋离线 CPU 降低 | 30.17% | 9.11% |

**波动不能省略：**boundary 相对 sparse 的端到端降幅范围为 **−12.56%～16.56%**，6 对中有 **2 对更慢**；相对 full 的端到端降幅范围为 **−1.15%～46.53%**，有 **1 对更慢**。这不证明 boundary 在每次运行中都最快，也不能据此建立可靠的成本决策模型。

这是共享本地执行环境里的短进程诊断试验，不是用户服务器测量、稳态服务延迟或统计显著性结论。准备块不预热后续新 JVM 的 JIT；未固定 CPU、未控制宿主负载。三种采集都明显慢于无插桩。RSS 原始值保留，但环境缺少 `/proc/self/statm`，监督进程内存下限未经核验，**不报告内存优势**。测量机制沿用阻塞等待和轻量原生 wait4 监督进程；缓冲写出不等于 fsync。

## 对论文的约束

目前 Java 和此前 Go 金额路径都提示：若已知完整入口状态，且剩余行为可在明确契约内重放，就不应预设内部探针必要。此轮没有证明 sparse 优于强边界重放控制组。

仍值得研究的是：如何判定入口证据是否充分，何时因未观测输入或模型缺口补充内部观测，以及如何根据完整成本选择方案。当前 Java 只提供一个支持这些问题的受控基线，没有完成字段级观测充分性分析、自动成本选型或真实 Java 应用验证。
