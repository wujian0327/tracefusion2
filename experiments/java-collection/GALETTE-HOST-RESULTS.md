## 完整成本

五组每次均运行原有 20 个输入两遍。六轮正式测量使用固定种子的随机顺序，
准备区组不计入中位数；本批 `jvm_warmup_rounds=0`，是新 JVM 短任务协议。

| 方法 | 在线耗时中位数（ms） | 离线耗时中位数（ms） | 总耗时中位数（ms） | 总 CPU 中位数（ms） |
|---|---:|---:|---:|---:|
| Native | 79.02 | 0 | 79.02 | 104.84 |
| full | 217.73 | 161.25 | 378.59 | 625.09 |
| sparse | 186.40 | 146.58 | 336.79 | 479.00 |
| boundary | 180.03 | 104.56 | 284.87 | 401.31 |
| Galette | 867.08 | 0 | 867.08 | 5,027.95 |

各列单独取中位数，因此阶段中位数相加不必等于总耗时中位数。
Galette 的标签传播和返回标签提取均计入在线阶段；总 CPU 是进程所有线程的
累计 CPU，包括 JIT 等 JVM 活动，可以大于墙钟耗时。

| 相对 Galette 的配对降幅 | 总耗时中位降幅 | 六轮总耗时降幅范围 | 总 CPU 中位降幅 |
|---|---:|---:|---:|
| full | 55.45% | 54.69%–57.95% | 87.74% |
| sparse | **60.71%** | 60.12%–62.51% | **90.39%** |
| boundary | **67.45%** | 65.67%–68.80% | **92.09%** |

六轮中以上三组的完整耗时和 CPU 均低于 Galette。内部控制组中，sparse 相对
full 的总耗时配对中位降幅为 **11.57%**，总 CPU 为 **22.65%**；boundary
相对 sparse 分别为 **17.13% / 17.54%**。这些比例从每个对应区组计算，
不是中位数之间直接相除。

## 能支持的结论与边界

**在这条固定来源查询路径、该 WSL2 环境和短任务协议下，我们的三种观测/还原
配置保留了声明的来源答案，并降低了相对 Galette 的完整部署成本。** 所有分析
组仍慢于 Native；boundary 仍是当前最省成本的分析配置，不能用本结果证明
sparse 的内部观测在此处必要。

必须同时报告：

1. Galette 广泛插桩 JCL 和应用，我们仅观察指定方法闭包。上述比例衡量指定
   查询的部署成本，不是等覆盖范围下核心传播算法的速度差异。
2. 总成本包含 JVM 启动、类加载/转换、输入准备、采集或标签操作以及结果输出；
   我们另含 Python 启动与离线还原。`WINDOW` 是诊断区间，当前没有同 JVM
   预热，不能称为稳态结果。CPU 型号、绑核和宿主背景负载没有在此协议中记录。
3. Galette 传播数组索引标签；我们的地址与直接数据依赖分离。这条路径的索引
   可能引入的 length 来源本来就直接参与数值计算，因此当前集合可比较，不能
   推广为任意程序上的语义等价。
4. 主机再次观察到 `-Xverify:all` 在 `AbstractStringBuilder.append(int)`
   处产生 `VerifyError`；默认校验启动成功。五组统一使用标准默认校验，未使用
   `-noverify` 或 `-Xverify:none`，严格校验兼容性限制必须保留。
5. RSS 仅保存原始值，不宣称内存优势。没有本次丢失证据或空输出问题。
