# Galette 外部对比：本地接入与完整成本核验（2026-10-12）

后续用户 WSL2 主机上传包已核验，见 [GALETTE-HOST-RESULTS.md](GALETTE-HOST-RESULTS.md)。
本文保留最初本地接入时的独立结果与当时状态。

**已跑通未修改的上游 Galette；这是真实外部工具对比。** 当前结果来自本地
执行环境，不是用户服务器结果，也不是整个 Java 应用或稳态服务评测。
复现方法和语义范围见 [GALETTE-COMPARISON.md](GALETTE-COMPARISON.md)。
机器可读记录见 [galette-local-validation-20261012.json](galette-local-validation-20261012.json)。

## 正确性

原版 Commons Codec 1.17.1 `MurmurHash2.hash32(byte[], int, int)`，复用原有
20 个输入；给全部输入字节、长度参数和 seed 独立绑定标签。

* Galette 默认 JVM 与 `-Xint` 各 20 个查询，合计 **40/40 正确**；TP=442、FP=0、FN=0。
* 直接读取并复核 **736 个输入值/标签绑定**，包含未读取的后缀字节；返回标签
  由外部工具实际传播产生，适配器不读取预期答案。
* 六个正式成本区组加一个准备区组，共 **35 次五组运行**，每次 40 个查询。
  所有返回值逐个核对；所有分析组的来源集合逐个核对。重复查询不增加场景覆盖。
* 重新推断我们三组的 **68,117 个原始事件**，复核 840 个根调用的实际源快照，
  并比较三组来源答案一致。
* 复核 **437 个证据文件**，所有保存的测量、随机顺序和配对汇总通过。
* 缺失返回、错误返回来源和错误输入标签三项解析器故障检查均拒绝。

外部正确性捕获复用自已通过的小规模接入运行，未再次执行这两次 JVM 正确性实验。
成本来自新的统一协议，未复用旧的三组 JDK 21 成本数据。

## 本地成本

同一个 Corretto **17.0.20.1+12-LTS** 基础 JDK；Galette 使用其独立插桩副本。
上游 Galette 固定提交 `bc6002cc5ee4d6eaa30518b2d176a9831d77cb1a`。
六轮测量采用记录在案的随机顺序，另有一个不计入中位数的准备区组。
每次新 JVM 执行 20 个输入两遍，本批未启用 JVM 内预热。

| 方法 | 在线耗时中位数（ms） | 离线耗时中位数（ms） | 总耗时中位数（ms） | 总 CPU 中位数（ms） |
|---|---:|---:|---:|---:|
| Native | 72.44 | 0 | 72.44 | 92.88 |
| full | 228.03 | 264.35 | 496.25 | 762.69 |
| sparse | 189.10 | 245.31 | 436.63 | 594.23 |
| boundary | 173.44 | 172.33 | 347.89 | 487.01 |
| Galette | 1,078.30 | 0 | 1,078.30 | 3,995.00 |

各列分别取中位数，所以在线与离线中位数之和不必等于总耗时中位数。
Galette 的传播与返回标签提取均发生在线上；“离线为 0”不表示其还原没有成本。

| 相对 Galette 的配对降幅 | 总耗时中位降幅 | 六轮总耗时降幅范围 | 总 CPU 中位降幅 |
|---|---:|---:|---:|
| full | 53.24% | 44.99%–60.37% | 80.94% |
| sparse | **58.06%** | 56.98%–63.08% | **84.66%** |
| boundary | **67.42%** | 63.01%–69.33% | **87.66%** |

三组均在这六轮中降低完整成本；boundary 仍优于 sparse。事件减少不作为外部
性能优势的替代指标，Galette 标签数量也不与我们的事件数作直接比较。

## 必须同时说明的限制

1. **启动与覆盖范围。** 这些是含 JVM 启动、加载/插桩、输入准备和输出的短任务
   成本。Galette 插桩 JCL 及更广应用范围，我们只观察指定方法闭包。
   可以报告指定查询的部署成本，不能据此声称核心传播算法本身快上述比例，
   或将数字推广到长时间服务。所有分析组仍明显慢于 Native。
2. **语义。** Galette 默认传播数组索引标签；我们的地址依赖与数据依赖分开。
   这条路径上索引可能引入的 length 标签本来就直接参与数值计算，所以这些
   输入的来源集合可比较；这不是所有程序上的语义等价证明。
3. **JVM 校验。** 未修改的 Galette 在 `-Xverify:all` 下出现
   `AbstractStringBuilder.append(int)` 的 `VerifyError`；标准默认校验可以启动。
   五组统一采用标准默认校验，没有使用 `-noverify` 或 `-Xverify:none`。
   两种启动探测的完整输出都保留，不能宣称严格校验兼容。
4. **内存和稳态。** 原始 RSS 保留但不据此宣称内存收益；内部计时窗口只是诊断。
   小规模接入运行验证过同 JVM 一轮预热，但没有证明 JIT 收敛，也没有正式稳态结果。
5. **归档失败不纳入结果。** 首个六轮批次有一个空 stdout；随后批次的最终清单
   未完整保存。这两批成本全部排除。原因尚未确定。随后使用父进程管道保存
   输出、原子保存 JSON，只有重新打开全部文件核验通过的当前批次进入上表。
   原始失败记录没有用推算内容补齐。

构建及静态选点不在业务测量区间。Galette JDK 插桩准备单列约 18.04 秒，不能
与短任务稳态时间混为一谈。当前构建复用了已成功构建、源目录无修改的固定提交 JAR，
这一点在准备记录中标记为 `build_reused=true`。
