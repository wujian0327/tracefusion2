## 环境与口径

主机使用 **OpenJDK 21.0.12.1**（Ubuntu build `21.0.12.1+1-1-24.04.4-Ubuntu`）。
Agent/驱动通过 `--release 17` 构建；Agent class major 61，原始 Commons Codec class
major 52。本次结果不能写成“在 JDK 17 主机测量”，也不能与之前的本地 Corretto 17
结果直接合并为一组重复测量。包中没有足够的 CPU 型号、CPU 亲和性、后台负载记录，
不据此解释不同机器之间的差异。

业务仍为原版 `MurmurHash2.hash32(byte[],length,seed)` 及其静态辅助方法。
来源边界是完整只读数组与两个整数参数；不是文件、网络或跨服务来源。
full/sparse/boundary 都使用相同 snapshot-v3 完整入口快照。

## 完整命令成本

每个业务命令调用原版哈希路径 **40 次**（20 组输入重复 2 次），所有返回值继续核验
来源。native/full/sparse/boundary 采用记录的随机顺序；1 个排除的准备块、6 个正式块，
随机种子 20261011。

| 中位数 | native | full | sparse | boundary |
| --- | ---: | ---: | ---: | ---: |
| 在线耗时 ms | 88.08 | 263.39 | 246.96 | 216.78 |
| 离线还原耗时 ms | — | 155.81 | 146.35 | 103.71 |
| 在线＋离线耗时 ms | 88.08 | 419.73 | 392.72 | 320.94 |
| 在线＋离线 CPU ms | 96.97 | 611.55 | 506.63 | 421.57 |
| 原始事件/命令 | 0 | 8,653 | 955 | 123 |
| 原始日志字节/命令 | 0 | 1,180,766 | 141,623 | 19,730 |

各阶段和总成本各自取中位数，不将阶段中位数直接相加。下表使用每个正式块内
`1 − 对比方法/基准方法`，再取六轮比例的中位数，与两个总体中位数的比值不同：

| 配对比较 | 事件降幅 | 总耗时降幅 | 总耗时降幅范围 | 总 CPU 降幅 |
| --- | ---: | ---: | ---: | ---: |
| sparse 相对 full | 88.96% | 7.23% | 1.15%–10.30% | 17.01% |
| boundary 相对 full | 98.58% | 24.36% | 20.78%–31.96% | 31.46% |
| boundary 相对 sparse | 87.12% | 18.28% | 11.69%–27.93% | 17.35% |

三种比较的总耗时在六轮中方向一致。但 sparse 离线耗时有一轮略慢于 full，boundary
在线 CPU 有一轮高于 sparse；不能说每个阶段每轮都改善。

这些数据支持本轮固定负载下的**完整命令成本**结论：在线包含新 JVM 启动、类加载、
ASM、记录和输出落盘；离线包含新 Python 进程、字节码解码、图构建、查询和 JSON 输出。
构建与静态计划不在计时内；CPU 为被测子进程的资源统计。每轮启动新 JVM，准备块
不能给下一进程完成 JIT 预热。不是稳态业务延迟、吞吐或单次哈希调用的开销，也没有
统计显著性、长期稳定性或外部工具比较结论。

主机报告中的 RSS 相对 supervisor 下限检查通过，这是合理性门槛，不等于独立测量
机制校准。boundary 的汇总也明确将内存比较标记为未验证。本报告保留原始 RSS 数据，
不据此提出内存优势主张。

## 对论文结论的影响

1. 在这个原版开源库路径上，稀疏采集保持声明的来源答案，并且相对完整采集具有实际
   时间/CPU 收益；事件减少 88.96% 对应的总耗时收益是 7.23%，不能等量替换。
2. 完整边界快照在当前有界、只读输入契约下仍然足够；边界重放在这批事件和完整命令
   成本上均更低。因此不能声称内部探针在该路径必需，或 sparse 优于这个边界控制组。
3. 所有采集组仍明显慢于 native。此批证据可写入“开源库路径正确性”和“完整命令成本”
   结果，不能扩张成完整应用、稳态服务性能、自动最优探针或对外部工具的优势。

不需要重跑已通过的正确性实验。后续性能评估应针对稳态执行与更完整的主机环境记录，
并持续保留边界重放控制组。
