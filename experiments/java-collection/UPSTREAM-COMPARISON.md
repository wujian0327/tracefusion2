# 原版 Commons Lang Java 路径：三组来源与完整命令成本

2026-10-10：直接运行 Apache Commons Lang **3.17.0 发布 JAR** 中的
`NumberUtils.max(int,int,int)` 和 `min(int,int,int)`。没有复制、裁剪或重编译上游
业务方法；驱动仅准备输入、调用发布 JAR、输出校验和。Agent 正常进行字节码插桩，
保存的原始 class 与 JAR 中的原始 class 逐字节一致。

这是**两个简单开源库方法的接入验证**，不是完整 Java 应用、复杂解析程序或整个
Commons Lang 的支持证据。此轮查询是整数参数到返回值的直接数据来源，不是对象字段
来源，也不追到驱动读取的文件字节。没有 FlowDist、MirrorTaint 或 libdft64 外部工具结果。

## 本轮补齐的能力

以前即使指定了查询入口，也会审查目标类的所有方法，因而被无关的数组、浮点数、
字符串重载阻止。现在显式 scope 下，独立 class 解码器按入口递归构建静态调用闭包，
Agent 只审查、插桩闭包内的方法；离线端重新解码原始 class，并检查闭包恰好一致。
**可达的未知操作仍拒绝，不会因未被当前输入执行就忽略。**

仍限于单一应用类中的静态调用闭包；没有自动补全外部调用、数组、异常、虚调用、
静态字段、长整数或浮点数语义。未指定 scope 时保留原来整个类的审查方式。类初始化、
无关库方法及驱动在声明的调用来源边界外；本次目标方法只读取三个整数参数，
不读取类初始化产生的静态状态。这不表示类初始化也已被溯源。

## 固定来源与独立真值

上游源码在比较中使用严格大于/小于，数值并列时保留更早的参数。独立 oracle 以
“数值极值、再按参数序号”排序定义预期来源；推断器只接收每次调用三个参数的标签
及返回值查询，不读取 oracle。推断从原始字节码和运行证据恢复被返回的参数定义，
不按返回数值相等猜来源。比较条件的影响继续与直接数据来源分开。

输入共 35 组三元组：`{-1,0,1}³` 的 27 组、`INT_MIN/0/INT_MAX` 的 6 种排列、
全 `INT_MIN` 和全 `INT_MAX` 两组。两个方法形成 **70 个不同查询**；default 与
`-Xint` 两种模式、三种采集方法构成 12 次真实 JVM 正常采集。不是 420 个独立场景。

| 采集/还原方法 | 正确查询（含两种 JVM 模式） | 原始事件 |
| --- | ---: | ---: |
| full | 140/140 | 1,844 |
| sparse | 140/140 | 572 |
| boundary | 140/140 | 292 |

三组全部返回值、来源、定义图及分支结果一致。采用相同 snapshot-v2 协议；这两个
入口只有整数参数，没有引用参数，所以字段快照项为零。boundary 只采三个完整入口
参数和返回值，不采内部路径或返回指令位置。全部整数参数已经足够重放这两条路径，
**不能用本结果证明内部观测必要或稀疏方法优于边界重放。**

负面检查包括：数组重载、long 重载、`createNumber` 和无 scope 的整类审查被拒绝；
实际 JVM 的数组重载采集也报告 unknown。四项离线故障（缺失返回、错误返回、额外
不属于闭包的方法、修改原始 class）均被拒绝。针对本轮修改另运行三组嵌套调用回归，
并确认删掉可达 `twice` 方法在独立解码器和实际 Agent 两处均被拒绝。

## 同负载成本

每次命令固定调用原始 `max` 350 次（35 组输入重复 10 次），全部 350 个返回值均
继续核验来源。native、full、sparse、boundary 按记录的随机顺序交错运行，1 个排除
的准备块、6 个正式块，随机种子 20261010；共 28 个业务 JVM 命令。

| 中位数 | native | full | sparse | boundary |
| --- | ---: | ---: | ---: | ---: |
| 在线命令耗时 ms | 91.17 | 250.53 | 253.22 | 233.65 |
| 离线还原耗时 ms | — | 156.25 | 155.87 | 146.30 |
| 在线＋离线耗时 ms | 91.17 | 408.38 | 413.64 | 378.68 |
| 在线＋离线 CPU ms | 103.74 | 579.93 | 549.09 | 504.35 |
| 原始事件/命令 | 0 | 4,583 | 1,403 | 703 |
| 原始日志字节/命令 | 0 | 578,745 | 181,539 | 91,403 |

各行分别取中位数，阶段中位数之和不要求等于总耗时中位数。配对降幅按每个正式
块内的比例计算，不是两个总体中位数的比值：

- sparse 相对 full：事件减少 **69.39%**，总耗时配对中位减少 **1.25%**，范围
  **−5.63%～16.31%**，**3/6** 轮更慢；总 CPU 配对中位减少 **8.75%**。
- boundary 相对 full：事件减少 **84.66%**，总耗时配对中位减少 **8.74%**，范围
  **3.37%～18.38%**；总 CPU 配对中位减少 **12.59%**。
- boundary 相对 sparse：事件减少 **49.89%**，总耗时配对中位减少 **4.46%**，范围
  **−0.14%～13.62%**，**1/6** 轮更慢；总 CPU 配对中位减少 **7.85%**。

这不是稳态吞吐或单次库调用延迟：每轮启动新 JVM，在线包含 JVM/类加载/ASM/记录
输出，离线包含 Python 启动、class 解码、图构建、来源查询和 JSON 输出。构建和静态
计划在计时外。准备块运行于独立进程，不能声称给后续 JVM 完成了 JIT 预热。
当前为共享本地执行环境，没有 CPU 绑定；内存机制核验未通过，**不作内存收益结论**。
所有采集组仍明显慢于 native。本轮只支持小规模完整命令成本观察，不代表服务性能，
也没有统计显著性或复杂程序扩展性结论。

还原图及逐文件哈希。

公开摘要：`upstream-validation-20261010.json`。原始证据目录：
`artifacts/java-upstream-20261010-100020-322190`。离线复核核对 **515 个文件**并重新
还原 **49,531 条原始事件**，包括正常采集和成本采集；不重跑业务程序。
聚焦方法闭包的新增回归另存 `artifacts/java-upstream-scope-check-20261010`，未修改原始
测量目录。原始证据目录被 git 忽略，公开报告不替代原始日志。

完整源码进行复核。后续应优先补数组、调用等真实程序所需语义，再选择更复杂的
未修改开源路径，而不是把两个简单方法包装成完整应用或扩大正确性计数。
