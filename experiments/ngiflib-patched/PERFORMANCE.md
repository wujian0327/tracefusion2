# ngiflib 完整命令成本对比

状态：**主机性能回传已核验，结果见 [PERFORMANCE-RESULTS.md](PERFORMANCE-RESULTS.md)。** 320 次正式在线测量和对应离线成本通过核验，完整墙钟配对中位降幅为 10.70%–48.94%，限于包含启动的统一边界快照任务。**当前峰值 RSS 受到父进程继承基线影响，不能用于内存比较，需修正后补测。** 下文保留实验方法与复现命令。开发环境仍无法启动 Pin；本地记录转换检查与真实主机结果分别保存。

## 本轮测什么

使用原始固定已修复 `gif2tga` 和既有四张正常图片、两种输出模式。未增加业务函数或图片，未修改上游传播器。比较以下四组：

| 组 | 在线过程 | 离线过程 |
| --- | --- | --- |
| native | 原始转换程序 | 无来源任务 |
| nullpin | Pin 下的原始转换，无来源分析 | 无来源任务 |
| boundary_replay | Pin 边界采集，不初始化 libdft 传播 | 校验记录、重放、写来源结果 |
| libdft64 | 原版污点传播、边界采集及返回标签输出 | 校验记录、提取标签、写来源结果 |

**这是包含启动的完整命令成本，不是稳态解码性能。** 每次运行都是新进程，在线计时包含 Pin 启动/JIT、转换及输出、采集文件写出和进程结束；本轮没有可靠分离 Pin 启动与解码时间，不相减估计。预热用于文件缓存和系统状态，不代表复用 Pin 的 JIT。小图片的结果可能由启动成本主导，不能推广成长时间服务开销。

构建、静态计划和工具编译分别记录，排除在逐次业务计时之外。离线过程另起 Python 子进程：完整耗时包括解释器启动、模块导入、读取/解析/校验、推断/标签提取、结果 JSON 输出和退出；另记录进程内部的解析、推断、输出分段时间。独立格式评分和像素核验在计时之外。完整串行任务的墙钟和 CPU 为在线与离线之和。原脚本记录两阶段峰值内存并取较大值；主机核验发现该高水位可能包含 exec 前继承的父进程内存，现标记为不可用于方法内存比较，不按理想化的目标进程峰值解读。

新适配器 `libdft_ngif_perf.cpp` 仅在函数入口/返回、读取调用/返回位置插入我们的动态观察回调。原版 libdft 仍执行其必需的指令传播。适配器不再逐条执行指令诊断、不写指令轨迹、使用缓冲输出并在结束时刷新；计时包括实际边界日志序列化及写出。没有 `fsync`，反映操作系统缓存写入成本，不等于持久存储延迟。

**两种方法支付相同的完整边界快照成本。** 对 libdft 而言，部分寄存器和上下文快照不是单独提取标签的最低必要成本。因此这是一项统一采集协议下的方法成本对照，不能宣称是经过最小化适配器优化的 libdft 总开销。必须把这个条件与数值一起报告。当前仍无 selected/eBPF 或 HardTaint 性能结果，来源语义限制沿用 `HOST-RESULTS.md`。

## 在已成功运行 Pin 的主机执行

```bash
git pull --ff-only origin perf/payment-steady-state
artifacts/ngiflib-venv/bin/python -m pip install -r experiments/ngiflib-patched/requirements-host.txt
artifacts/ngiflib-venv/bin/python experiments/ngiflib-patched/performance.py run
```

沿用此前的虚拟环境。依赖自动复用 `artifacts/external-tools` 下固定 Pin、libdft64 和 ngiflib checkout；路径不同可传 `--pin-root`、`--libdft`、`--source`。需要 Linux amd64、GCC/G++、make、binutils、Git 和 Python，无需 sudo。运行时尽量停止其他高负载任务，不需要修改频率策略或清空系统缓存。

默认 2 轮预热、10 轮正式测量：8 个图片/模式组合 × 4 组，共 64 次预热、320 次正式在线运行；两种来源方法每次另测离线进程。用固定种子随机化用例顺序和组顺序，原始顺序写入 `schedule.json`。自动选择允许 CPU 集合中的第一个逻辑 CPU，并让测量子进程继承相同亲和性；可用 `--cpu N` 指定允许集合中的其他 CPU。不保证该核心没有系统负载，保存环境和原始波动供复核。

可调整 `--blocks 20 --warmups 3 --seed 20261010`；最低要求 3 轮正式测量、1 轮预热。`--timeout` 是单个子进程的上限，默认 180 秒。每个用例开始都会打印进度。执行失败也会保留日志并打包，失败的整轮不会标记为完成；不丢弃失败样本后静默报告成功。

结束会打印 `Return this result archive: .../ngiflib-performance-....zip`。请回传整个 zip，成功或失败均可。原始记录、逐次 `wait4` 墙钟/CPU/峰值 RSS、离线结果与分段耗时、输入/ELF、源码/工具身份和汇总均保留。

## 正确性与统计规则

- 每次运行核对转换像素；同一配对块的四组标准输出和 TGA 必须相同。
- 两种来源方法每次都完成完整记录校验并生成来源结果。我们必须与独立格式参考精确匹配；libdft 必须复现已核验原版标签结果，包括既有额外来源，不能为了计时跳过失败或改用空标签。
- `perf_records.py` 是单独的成本记录协议。标志不符、残留指令诊断、计数不符、读取/调用不完整、未知标签、上下文变化等均拒绝。它不伪造指令轨迹来满足旧核验器。边界重放仍有指令执行上限和未知行为拒绝。
- 两种方法在线同进程内的业务、Pin 和采集 CPU 无法准确拆开，报告整体；不把进程总 CPU 冒充纯采集 CPU。
- 预热行保留但排除于汇总。每个图片/模式分别报告中位数、最小值、最大值和 p90，不把不同输入混成独立重复样本。
- 保存逐块配对的在线和完整成本降幅，正值表示重放更省、负值表示更贵；报告配对中位数。另报告各组相对 native 的在线墙钟倍数。10 轮结果不是统计显著性证明。

`summary.json` 只有 `stage=performance_complete`、`all_results_checked=true` 时才是完整候选性能结果。它仍需回传后从原始测量重算、核对来源和身份，才能成为已核验结果。请勿将准备阶段 `build-tools` 输出或 `performance-local-validation-20261010.json` 当作加速比。现有包已完成该核验，无需重跑；见 `verify_performance.py`。

## 本地验证边界

新适配器已在固定 Pin 3.20/libdft64 上编译链接，上游 33 份源文件保持一致。17 项检查涵盖：从旧真实日志移除诊断后的双方 416 次查询协议等价、10 项故障拒绝、独立重放子进程及资源计量、非零退出/超时拒绝、可重现调度，以及“在线更快但离线导致总成本更慢”时统计正确显示反转。旧记录转换不是新适配器实际运行，动态回调位置还需主机结果验证。
