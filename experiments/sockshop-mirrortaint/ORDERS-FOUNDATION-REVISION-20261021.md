# Orders 统一执行入口与保守构造器效果

**本轮修复了通用执行语义和证据分类缺陷，但没有新增修复 Orders 的基线领先实例。** 最终核心冻结为 `0956200b622c6ed8cba97b2762fd31e222a8584b`。原版 Orders 的 Date 和 username 两个查询均能进入统一内核、完成实际执行及独立真值核验；full/selective 每个查询各6个目标仍全部 unknown。计划接纳不等于来源答案成功。

业务继续使用原版 JAR，九个 JAR 哈希不变。没有性能实验，没有启封29个候选。原169个基线领先实例的开发台账仍为累计修复97、剩余72；本轮不改写以前的覆盖结果和成本表。机制见[算法说明](ORDERS-FOUNDATION-ALGORITHM-20261021.md)。

## 本轮实际修复

1. **构造器的保守分类与生命周期。** 无法解释的构造器记录不透明效果，而非让未执行分支中的异常构造器阻断整个入口。实际执行时核验开始、唯一ID、正常/异常完成及实参；未初始化接收者不传给监测器。未知效果仍使可能受影响的字段失效。
2. **内部类初始化边界。** 编译器可在 `super` 之前写入 `this$0`，当前采集器无法提供对应的初始化后写入证据。赋值快捷规则现在保守拒绝此形态，转入不透明构造器，不根据最终相同值补造一次已知写入。
3. **静态读取和本地字符串构造。** 记录实际 GETSTATIC 值，保留外部初始化效果屏障；接入固定 JDK 的 StringBuilder 标量追加和字符串返回。`append(Object)` 的应用 `toString` 候选由字节码发现并按实际 Frame 解释，未知渲染仍有屏障。补齐 long/float/double 常量及字符代码单元证据。
4. **可变参数的完成状态。** 未知构造器可能正常修改 Date 参数。先保守失效再检查完成后的状态，保留引用身份与开始时快照检查；不把这种未解释的修改误报为证据损坏。此前已复制的不可变标量可以保留来源。

这些规则由指令、类型、身份和效果驱动，未增加 Orders 字段名专用传播代码或来源匹配表。查询仍声明入口、目标/响应路径和来源边界。

## 原版 Orders：端到端答案仍未打通

两个查询来自已暴露开发集，同一入口、同六种输入结构：正常单商品、同值商品、空购物车、零单价、修改后输入及重复结构。依法通过原业务注册/准备新的客户和购物车标识；四个配置复用相同实际输入、请求体和消息坐标。环境生成的日期允许不同，未将其用于同值匹配。

| 查询，每种配置各6个目标 | full 已知 / unknown | selective 已知 / unknown | 可回答率 | 证据无效 / 真值不可用 |
| --- | ---: | ---: | ---: | ---: |
| `/date` | 0 / 6 | 0 / 6 | 0% | 各0 / 0 |
| `/customer/username` | 0 / 6 | 0 / 6 | 0% | 各0 / 0 |

每种配置共12个实际目标；两种配置的24行实例分开保存，不当作24个独立新查询。没有已知答案，条件来源完全匹配率为 N/A。username 的每个目标有一个独立来源关系；将 unknown 阳性也计为漏检时，每种配置这6个实例为 **TP0 / FP0 / FN6**。Date 的字段边界来源为空，仍有环境时间事实；其 FN 为0不能解释为“空来源已答对”，六个目标仍未回答。

Date 真值根据原业务 Calendar 调用、实际 Date 对象和目标字段版本确定，并独立转换客户端 ISO 时间。username 真值使用已审阅的原代码、对应实际 HTTP 调用、完整原始 JSON、默认 HATEOAS 解码后的物理字段及对象/版本，核对其与响应字段的身份关系。两者不使用 TF 传播、图遍历或 MirrorTaint 标签决定预期来源。

原始 HTTP 字节旁路对本轮两配置均启用，用于独立真值和诊断；它不会自动创建来源边。没有用这些运行估计成本，也没有将额外原始字节的成本混入旧性能表。

## 剩余断点的含义

实际执行的不透明环节包括 AsyncGetService、Future.get、HATEOAS Resource 内容/链接访问、保存，以及部分 URI、正则、集合或 Date 渲染。完整列表在审计的 `executed-opaque-calls.json`；它是执行清单，不是最小因果切片，不能把某类调用次数直接换算成修复后成功数。

username 的读取链仍缺少“提交任务—工作执行—完成—Future 获取”的实例连接及受核验的解码投影。Date 的环境生成已经能解释，但后续不透明渲染、保存等效果尚无保持依据。保存仍可能写 ID/version 或运行回调；返回同一对象、值不变或相同 trace 均不足以证明其他字段未受影响。

因此，这轮进展是**统一内核能覆盖入口执行，并正确保留未解释状态**，不是两条来源链已经修好。后续需要独立任务协议、解码与字段效果模型；不会通过忽略调用、移动源边界或读取返回快照消除 unknown。

## 冻结、失败与复用

协议提交 `240d7b4` 先固定范围与查询，见[协议](orders-foundation-protocol-20261021.json)。业务捕获使用初始冻结 `6d783c6` 的 Agent 与计划，共28份。补充控制发现未知构造器修改 Date 参数会触发错误的证据分类；修复后冻结 `0956200`。两个版本及源码包都保留。

最终修订只修改离线状态处理。重新构建 `final-validation-build/` 后，逐份核对捕获使用的计划与最终生成计划完全一致、Agent 全部 class 哈希一致，再使用最终离线代码复算。实际原 Agent、计划、build 清单及初始提交仍保留于各捕获目录；`audit-final/capture-reuse.json` 保存证明，不把复算称为新部署。

控制程序在计划与 Agent 一致时复用已有捕获，见 `control-reuse.json`。原失败保留在 `semantics-development-01/02/06/`、`business-development-01/` 和 `opaque-date-first/`，其余开发检查点亦保留。开发捕获在变化后的计划上做过离线定位，仅用于诊断；正式 Orders 使用冻结后的重建与新部署。

一次 Cart 启动命令的构建路径笔误产生重复 setup，并遇到端口占用；该失败单列 `cart-gaps-frozen/`，已清理，不计作算法失败或成功。正式结果只读取 `cart-gaps-frozen-final/`。
