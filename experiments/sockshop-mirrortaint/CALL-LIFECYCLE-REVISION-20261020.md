# 调用配对修复、冻结与新成本验证

本轮修复有限读取监测器的异常调用闭合，停止扩展 Orders 保存/异步、一般循环和类型语义。算法冻结为 **`2b3b9297e8382162865075d22459480980a45bbc`**。此前 c3e6739 的覆盖结论、两批 Basic 失败及14个无效目标原样保留；本轮运行是开发可靠性回归，不是新的封存覆盖测试。

方法条件见[调用生命周期与效果核验](CALL-LIFECYCLE-ALGORITHM-20261020.md)，成本口径见[冻结协议](CALL-LIFECYCLE-COST-PROTOCOL-20261020.md)。[新成本完整结果](CALL-LIFECYCLE-COST-20261020.md)已完成，原始根目录亦有 `results.md`；本报告不搬用旧成本表。

## 修复内容及判定

原实现只在正常返回时弹出调用状态，异常后留下未闭合调用；根 abort 也没有清理该监测器。v2 增加每次原 invoke 的异常完成，重抛原 Throwable，保留业务 handler/finally；根正常或异常退出均记录 summary 并清理状态。离线端校验唯一调用身份、严格嵌套、总数、根退出与 summary 的一致性。

完整但不透明的效果保持 unknown；未闭合、丢失或矛盾证据仍拒绝整批。本轮没有实现按请求忽略坏证据。异常配对成功不代表取得只读效果证明，也不创建来源。

## 原始 HTTP 字节的成本边界

Cart/Train 的 full/selective 在 source_evidence 开、关下独立校准均匹配，每配置另有8项必要证据破坏检查。它们使用仓储来源，没有实际下游原始 HTTP 读取事实，此处不宣称关闭该开关能减少多少开销。

真实五服务票价在开启时每配置捕获157个 `http-source-fact`；full/selective 各38个答案与独立真值一致。仅移除这些额外事实后，对象/字段/版本/消息来源答案保持不变；移除必要源字段或引入歧义 RPC 仍拒绝或 unknown。独立关闭配置也各38/38匹配。

因此新成本主配置关闭额外原始字节旁路，保留所有必要 HTTP/JSON 字段、调用效果、身份版本、响应/序列化绑定及核验成本。这里验证的是诊断独立性，不是 raw-on/off 性能比较。

## 失败保留、审计与工件

原始根目录：`artifacts/call-lifecycle-revision-20261020/`。重要节点逐版记录于 `logs/00…`；算法源码包、冻结哈希、Basic混合、语义、历史业务、三类成本、静态规划及独立审计均在此目录。

新增验收脚本首次将 Train 未使用的第一次读取误作必需来源扰动，断言失败；随后按原逻辑改为第二次读取。另一次静态计时提取漏掉实际基准模型已有的 Response 依赖类，计划等价检查主动失败；修正计时驱动后全部15轮在新目录重新测量。两次均未修改冻结算法；首次日志和不等价测量留在 `logs/*first*`、`static-planning/`，不进入正式表。

在线驱动复核还发现Cart/Train初始计时包含客户端解码/记录落盘；修正为HTTP响应读取完成即结束，并用实际HTTP控制程序验证排除延迟的解码和落盘。`cost-cart/`保留为该修订前试运行，不进入正式表；Cart正式组全部在`cost-cart-final/`重测。Train及票价正式组不受旧试运行影响，已有校准和静态测量继续复用。此处仍未修改核心算法。

内存控制实验确认本机`ru_maxrss`会继承父进程的高水位：父进程分配100 MiB后，一个新exec小程序的ru_maxrss约110 MiB，而自身VmHWM仍约10 MiB。因此保留原始计数为启动口径，不用它声称实际离线处理峰值。在线实验结束后，用全部30份来源捕获独立复算并读进程自身VmHWM；评分必须逐份相同，原始捕获、答案和计时不得覆盖。正式RSS表按该复算口径单列，不重新部署业务。

历史表若使用同类ru_maxrss计数，仍须按其原启动口径解释，不能直接与新VmHWM横比，也不能在未经核验时称为exec后处理峰值。本轮不改写旧原始数据或自动重跑旧业务；论文沿用旧RSS结论时需要单独复核计量口径。

完整数据不随 Git 自动同步；后续迁移需另行备份，并在新目录重新构建。推送交给用户。
