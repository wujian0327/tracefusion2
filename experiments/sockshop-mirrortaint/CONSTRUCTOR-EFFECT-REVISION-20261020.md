构造器支持限定为直接完成空Object初始化后的主体，以及有界同类委托到可解释赋值构造器。日志工厂限定固定slf4j/default logback环境；过滤限定固定具体List、单个filter、顺序findFirst及已支持的Predicate方法体。一般super前缀、框架构造器、保存与异步继续受限。

所有查询仍统一启用 `execution_kernel` 和 `application_calls`；本轮没有新增逐字段业务开关。人工新增的是公共库契约、固定版本和独立评价代码，不是预期来源映射。旧profile保留。

## 原15个Cart差距的真实业务验收

使用原版Carts与Mongo、原能力对照的六组输入。合法API准备一次共享输入数据库，随后独立轮换目标JVM；先完成全部full查询，再运行全部selective查询。每个查询实际生成5个目标；空商品列表那组返回原业务的未找到错误，没有目标，单列N/A。

| 查询 | full正确 / 实际目标 | selective正确 / 实际目标 | 每配置TP / FP / FN / unknown |
| --- | ---: | ---: | --- |
| ItemsController.get → quantity | 5/5 | 5/5 | 5 / 0 / 0 / 0 |
| 同入口 → itemId | 5/5 | 5/5 | 5 / 0 / 0 / 0 |
| 同入口 → unitPrice | 5/5 | 5/5 | 5 / 0 / 0 / 0 |
| 合计 | **15/15** | **15/15** | **15 / 0 / 0 / 0** |

三个查询共一个入口，不能写成三个独立入口泛化成功。每配置18个原“查询－请求”、15个目标和3个N/A请求；每次部署都另有一个保护请求，下面分开统计。

独立真值依据原代码、合法准备后的实际商品列表、客户端指定itemId及本次实际仓储返回。按准备列表定位原始输入成员，再投影实际源字段、对象、版本、调用及消息坐标；不调用TF依赖传播或图遍历来决定预期来源，也不读取MirrorTaint标签。

审计逐项核对原基线运行的请求路径、请求体、HTTP状态和输入商品事实，以及原15目标的客户端值。不同JVM的Mongo生成ID、对象ID和事件序号按各自实际执行评分，不跨运行比较这些ID。
