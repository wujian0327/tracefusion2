**冻结版在原版 Station 和 Route 的四个开发查询上，full 和 selective 各正确回答 60/60 个目标实例；额外真实业务保护输入各 32/32 匹配。** 这组修复覆盖原能力对照中的 60 个循环反例。保存、异步、数组、lambda、Date 及通用跨方法解释尚未实现，整体 382/431 验收仍未达到。

算法冻结为 `bc69ebe2ce0e9355b8383879a6c34421ea66d01c`。原版九个业务 JAR 哈希不变；实际部署只使用原 Station、Route 服务及各自 Mongo。原 `2b3b929` 的 [431 目标首轮结果](BASELINE-CAPABILITY-20261020.md)、历史成本及首次失败没有改写。剩余 29 个候选在本轮任何核心改动前封存于 [协议](execution-kernel-protocol-20261020.json)，没有尝试规划或执行。

## 已实现的机制

新配置 `execution_kernel: true` 启用统一执行路径；旧复制、归约、集合、标量和返回转发 profile 保留。该开关是查询执行策略配置，不包含预期来源、业务公式或实例匹配表。四个试点查询统一使用同一开关与规则。

静态分析沿控制流图迭代合并局部变量与操作数栈的可能定义，允许回边和 IINC，达到有限不动点后生成计划。原 profile 默认仍拒绝循环；没有全局删除旧拒绝检查。新路径明确检查自己具有还原语义的指令和构造器，其余直接拒绝。

离线状态统一表示 Value、Frame、State、Call 和 Container。每个实际根调用有独立局部变量、栈和程序计数器；字段依赖按对象、字段与实际写入版本存储；列表维护对象、顺序元素和内容阶段；迭代器绑定实际列表及下一位置。中间值携带来源、选择证据、未知标记和分配身份。新字段复制、setter、窄构造器和列表追加都使用这些状态，不按业务字段名称写传播代码。

首版的跨方法支持仍依赖从字节码核验的 getter/setter、参数赋值构造器及有限公共契约，**不是任意应用方法的递归解释器**。已解释的 setter 可以只更新对应字段依赖；同值常量覆盖产生新版本及空数据来源。不相关字段的已解释写入不会自动污染另一个目标。尚未解释的一般调用仍施加保守屏障，字段敏感的通用调用效果分析尚未完成。

运行端记录根方法调用的接收者、参数、结果、正常或异常完成、分支、字段读取与必要写入。构造器证据只在原 invokespecial 成功后读取已初始化对象，不能把未初始化引用传给监测器。每个完成根的调用序列必须闭合；异常前未进入被调方法也有异常完成，异常后正常请求继续独立核验。

List/Iterator 契约固定具体实现及 [JDK 类哈希](execution-kernel-runtimes-20261020.json)。列表追加必须作用于本地、未逃逸的受支持列表，并核对追加前后内容和阶段；Iterator.next 必须返回绑定列表当前位置的实际成员。Route 输出第 j 个成员由实际 add 的输入对象决定，不以输出下标替代输入下标。条件和索引的运行证据保留，数据来源仍不混入一般控制依赖。

来源只由原声明的入口、仓储读取返回、实际 RPC 读取边界提供。当前试点的叶来源来自具体仓储读取及其字段/元素。还原结果以来源证据坐标写入统一图，再由实际返回对象及序列化字段的身份和版本核验目标绑定。返回快照不创建来源，数值仅作一致性检查；必要来源缺失或歧义保持 unknown，缺失调用完成等损坏证据直接拒绝。

这一组织方式参考了 MirrorTaint 对栈、堆和跨帧状态的统一组织；TF 当前试点仍在离线计算依赖，且保留自己的实例证据坐标。[MirrorTaint 原论文](https://zhangyuqun.github.io/publications/icse2023c.pdf)

## 冻结后的原版业务结果

四个查询均来自已暴露开发集，不能当作新的未见查询泛化证据。每个查询使用原能力对照的六组冻结结构，与先前基线的请求、数据库文档和实际响应逐项核对；每套件先完成全部 full，再运行 selective。额外保护套件使用独立端口和数据卷，可与普通套件并行，因此没有从部署时间推断性能。

| 原能力对照中的查询 | full 已知且完全匹配 | selective 已知且完全匹配 |
| --- | ---: | ---: |
| Station.queryByIdBatch → /data/* | 10/10 | 10/10 |
| Station.queryForIdBatch → /data/* | 10/10 | 10/10 |
| Route.getRouteByStartAndTerminal → /data/*/stations/* | 30/30 | 30/30 |
| 同入口 → /data/*/terminalStationId | 10/10 | 10/10 |
| 合计 | **60/60** | **60/60** |

两配置各 24 个“查询－请求”、TP60/FP0/FN0/unknown0，另各 4 个请求没有元素目标。列表查询族与元素实例是不同分母。两个 Route 字段来自同一入口，四个查询共三个入口。

额外保护套件沿用相同四个查询和原版 JAR：Route 仅保留中间成员、仅保留末尾成员、非相邻成员、全部过滤及空库；Station 缺失项在前、重复读取、请求重排、全部缺失、空输入及后续正常请求。**full/selective 各 32/32 来源集合匹配，TP30/FP0/FN0/unknown0**，另各 7 个请求没有目标。其中两个目标是原业务的固定回退字符串，数据来源为空，不是 unknown。

独立真值由原业务逻辑、实际数据库事实、原始调用区间及对象/字段坐标生成：Station 明确选择对应循环迭代的仓储返回；Route 先按原代码条件确定被保留的原始记录，再投影字段或元素。它不调用 TF 的依赖传播、图遍历或 MirrorTaint 标签决定预期答案。

两套件共 16 次独立服务部署；普通与保护输入分别报告，不将新增保护目标塞回原 431 的分母。

## 正确性保护与历史回归

- 新 JVM 小程序 full/selective 各 16 个有效目标：15 个预期已知且独立来源匹配、1 个必要 helper 保持 unknown；另各 1 个异常根没有返回目标。覆盖同值不同对象、计数与迭代器循环、空列表、字段复制、无关字段写入及同值常量覆盖。
- 新小程序 16 项证据扰动保护通过；原版 Route 捕获另有 5 项身份、返回版本、调用完成、缺失来源与歧义来源检查通过。缺失或歧义来源不能变成确定的空来源。
- 新 Agent 运行旧集合语义 full/selective 各 10/10 匹配；旧绑定 54 项中 48 项预期已知匹配、6 项预期 unknown；旧调用生命周期各 11 个有效目标中 7 个已知匹配、4 个预期 unknown，并保留原异常和中止保护。
- 原能力对照中 TF 实际执行的 301 个目标，使用原 Agent、原计划和原始捕获在新离线代码上复算：213 个正确、88 个 unknown 均保持原状态。**这不是 213 个目标的新部署验证。**

没有将旧 213 个正确目标与新 60 个目标直接拼成“新版全量正确率”，也没有宣称覆盖全部基线正确实例。原 382/431 的联合验收条件继续保留，不能用本试点替代。

## 当前边界与后续阶段

新路径当前只解释受支持的根方法及有限调用契约，执行步数有界；根内 catch 处理、数组、lambda 体、保存、异步任务、Date/随机生成及任意库类型仍拒绝或 unknown。共享可变对象并发、反射/native 写和自定义序列化继续超出保证。

selective 首版保守保留全部已建模根调用、分支、字段读取和必要写入。full 与 selective 使用相同核验规则，但本轮没有做查询切片收缩或成本比较。旧成本表不能用于新路径。

接下来仍需按协议完成一般调用的字段效果与参数/返回传递，随后补实际所需数组/lambda、保存/异步及解码规则；这些工作不能用只读白名单替代。29 个候选要等新支持形态和版本再次冻结后才启封。
