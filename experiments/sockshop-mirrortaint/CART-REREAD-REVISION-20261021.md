# Cart 首次创建与再次读取来源修订

**本轮打通 Cart 的“创建、保存、再次读取”目标链，但没有将保存声明为只读或来源保持。** 核心冻结为 `014f18da49a8636810f653662d3edfb86de5f2ee`；实际来源仍是原边界下的仓储读取返回字段。所有业务部署使用原版 JAR，九个 JAR 哈希保持不变。

新增机制是有界 helper 调用图和对象创建时刻证据，详见[算法说明](CART-REREAD-ALGORITHM-20261021.md)。本轮继续保守采集必要证据，未做切片收缩、性能实验或未见查询测试。29个候选仍封存。

## 原问题与修订

空 Cart 的回退函数执行创建和保存，随后再次进入读取 helper。先前规划器因调用图有环，将这个 lambda 体排除为不透明；即使能够进入调用，旧效果失效集合还会预先包含稍后才创建的来源对象。

现在每个方法只生成一份静态分析结果，实际每次调用有独立 Frame。默认深度64层、每根累计100000步；超限为 `analysis_limited`。入口自身重入、未建模指令、同步和并发共享效果仍有限制。

对原字节码以空 Object 初始化开始、且已纳入计划的构造器，记录实际对象、构造器 Frame、事件序号和类哈希。更早已完成的不透明效果不能触及尚未创建的对象；缺少这个证明就保留原有保守屏障。保存参数、保存返回对象、旧别名和创建后的不透明效果没有获得豁免。

**创建证明不产生来源。** 新读取对象的来源仍需由真实仓储调用、对象、字段和版本落地；响应快照只绑定目标。首次 GET 的目标连接第二次读取，后续 GET 连接本请求第一次读取，不能按相同 customerId 猜来源。

## 冻结后原版业务结果

| 套件 | full 已知且完全匹配 | selective 已知且完全匹配 | 统计范围 |
| --- | ---: | ---: | --- |
| 原基线首次创建与后续 GET，两请求 | 2/2 | 2/2 | 使用原对照客户ID；其中仅首个目标是原能力缺口 |
| 混合客户创建与重复读取 | 7/7 | 7/7 | 3次创建、4次重复，另列保护输入 |
| Station/Route 循环 | 60/60 | 60/60 | 原4查询、3入口 |
| TicketInfo 包装与真实 RPC 返回 | 21/21 | 21/21 | 原同入口3查询 |
| Cart 单项 GET | 15/15 | 15/15 | 原3字段查询 |
| 旧 Cart 列表读取的统一内核路径 | 6/6 | 6/6 | 原1个查询 |

混合套件使用三个预先固定的新客户标识，每种配置均从新空库开始，输入顺序相同。它用于检查创建、重复和请求间隔离；驱动中的同值标记指同一客户的创建/重复配对，不表示不同客户的七个值全部相同。另行使用原431目标对照中的客户ID `56e8f576709b70d0ace01fb0`，复现原首次创建及重复 GET；该输入和驱动哈希在这次部署前单独保存于 `baseline-pair-protocol.json`，核心此前已经冻结。

独立真值根据原业务调用顺序和原始读取区间选择实际来源：第一次空读取没有实体目标，保存后第二次读取的实体字段对应返回字段；重复请求只有第一次读取。检查实际目标和源字段的对象及版本，检查调用开始、读取快照与完成的顺序。保存结果实体与再次读取实体不同，构造器创建事件位于所有保存完成之后、对应读取区间之内。真值选择不调用 TF 传播、图遍历或基线标签。

本轮只将原169个基线领先实例中的 **1个**首次创建反例计为新增修复。开发台账累计97、剩余72（Orders普通字段66、Date字段6）。额外请求不加入原431分母，也不把旧213与阶段修复数直接相加作为新版正确率。最终62查询、同版本 full/selective 的联合验收仍未完成。每个查询仍声明入口、目标/响应路径和来源边界；本轮没有增加单字段传播公式或实例匹配表，构造器观测位置与调用边从固定字节码生成。

## 语义与保守处理

- 独立 JVM 控制 full/selective 各16个目标：8个已知且来源完全匹配，另8个不透明修改、旧对象或旧别名目标保持 unknown。已知项包含已建模常量，其空来源与 unknown 分开。
- 控制程序各6项扰动检查通过；调用深度预算耗尽为 `analysis_limited`。实际 helper 循环捕获的入口重入分析检查亦返回 `analysis_limited`，该检查是离线能力限制控制，不是新增业务部署。
- 真实 Cart 各7项证据扰动：去掉创建证明、缺少或歧义来源退回 unknown；错误对象、哈希和重复创建记录拒绝。错误 Frame 无法提供创建证明，亦不能保留确定答案。
- 原应用调用控制各26个已知匹配、8个预期 unknown、2个异常根；构造器控制各20个已知匹配、4个预期 unknown、2个异常根。保护案例不合并成来源准确率。
- 旧集合 profile 的新 Agent 控制各10/10匹配，indexOf篡改、接收集合修改及虚调用保护通过；最早 selective 缺失构造字段写入的永久失败捕获在新离线代码上仍被拒绝。
- 旧301个原始捕获在新离线代码上保持213正确、88 unknown。它们使用旧 Agent 和计划，属于离线兼容复算，不是213个目标的新部署。

## 冻结、首次失败与评价修正

协议先于核心改动提交，见[固定协议](cart-reread-protocol-20261021.json)，提交为 `3fa9d61`。原62查询、431目标、旧成本表及以前的失败结果不改写。原始目录为 `artifacts/cart-reread-revision-20261021/`。

开发首轮 `business-development-01/` 捕获了未限定到匹配构造器 Frame 的创建事件，严格核验因此失败。之后将观测限定到已计划构造器，并核验实际 Frame、接收者和哈希；`business-development-02/` 与语义控制通过后才冻结。原失败的计划、Agent、事件及后续成功捕获均保留。

冻结后只修改审计评价代码：完成事件只存 call-id，需要与开始事件连接才能取得 callee；一次保存同时有 DAO 和 Repository 两层完成，不能假设只有一条 save 记录。原评价代码保存在 `audit-evaluator-at-freeze.py`；冻结清单中的该文件哈希由原副本核验，当前评价器另留哈希。规划器、Agent、还原器和配置的冻结哈希没有变化，也没有为通过审计改写原事件。审计还单独检查了原客户ID的两请求复现。

重要节点位于 `logs/00…`；`algorithm-freeze.json` 固定源码、九个业务JAR与封存协议哈希，`candidate-code-014f18d.tar.gz` 保存冻结源码。新 Agent 的兼容回归重新部署；旧301捕获仅离线复算，分别报告。
