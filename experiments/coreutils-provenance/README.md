# 真实 C 程序的来源查询预注册与接入评估

## 状态

这轮完成**候选选择、查询与独立真值定义、原程序输出预检**。尚未运行两种方法的来源推断，不是新的溯源准确率结果，也没有性能结果。此前 C/libdft64 的 24/24 正确性结果仍仅适用于原受控场景。

候选版本为 GNU coreutils 9.4，上游固定提交 `9530a14420fc1a267e90d45e8a0d710c3668382d`。当前原生预检运行的是开发环境已有的发行版 9.4 二进制，记录版本和 ELF SHA256，但未认定与上游源码构建完全一致。正式对比必须构建固定源码，保存构建参数、依赖版本、二进制和反汇编，两种方法使用同一 ELF。

## 为什么选这两个程序

| 对象 | 来源查询 | 有区分力的行为 | 不支持的论文外推 |
| --- | --- | --- | --- |
| `cut` | 输出字段对应哪个输入文件、记录和字段 | 同值选源、互补选择、多文件、重复记录、首字段缓冲、长字段和无分隔符路径 | 不证明复杂算术或网络服务支持 |
| `join` | 合并结果中的字段来自哪个文件和哪个记录 | 两文件同值字段、反向投影、重复键多对多匹配、未匹配行和常量填充 | 不等同于数据库内部行级溯源 |

HardTaint 使用过 `cut` 所属的 Unix 工具类别；这里额外选择 `join` 是因为它适合检验多输入字段身份和记录选择，不声称 `join` 是 HardTaint 的既有基准，也不预设我们能胜出。

原始程序不修改，不抽取并简化业务函数，不把小型自写替代程序作为真实应用。测试通过原始 CLI 和完整进程执行；测量阶段再明确初始化与稳态的口径。

## 先固定查询，再运行方法

`prepare.py` 固定了 16 个用例：cut 10 个，join 6 个。输出包含 35 个字段来源查询、37 个无输入字段来源的片段查询（分隔符、换行、填充文本）以及 2 个无输出用例。零起始来源 ID 为 `文件序号:记录序号:字段序号`，同时给出实际文件字节偏移和长度。

所有输入字段负载都可以被标记，包含 join 的键和未输出的 noise 字段；目标查询仅比较显式数据来源。被用作匹配或选择条件的键不因参与控制就自动成为负载输出的直接数据来源。输入分隔符、行分隔符和 CLI 配置不在标记集合中，故输出分隔符的空集合含义是“没有已声明输入字段负载来源”，不是声称其没有任何配置或控制依赖。

预期结果按明确的文件/记录/字段位置构造，**不通过输入输出值相等寻找来源**。字段值刻意重复。真值只供评分器读取，后续静态选择器、观测器及两种传播引擎不得读取 `expected_pieces` 或 `queries.json` 中的答案。可以读取来源身份与字节范围以设置同一 source 边界，但不得读取目标来源映射。

`prepare.py` 只验证业务输出；它无法证明输出片段具有所声明的机器级来源。因此 `provenance_checked`、`bpf_executed`、`libdft_executed` 和 `performance_eligible` 均固定为 false。正式接入后还须审计原始路径与参考语义是否对齐，并独立检查错误来源、缺失事件、过度传播及 unknown，不能把业务输出匹配当作来源正确。

## 本地预检

```bash
python3 experiments/coreutils-provenance/prepare.py --output artifacts/coreutils-preflight
```

输出目录必须不存在；命令要求本机 GNU coreutils 9.4。没有该版本时暂不在用户机器安装或替换系统工具。开发环境已完成预检，见 `native-preflight-20261010.json`：16/16 原生输出匹配。后续正式运行器应使用单独构建的工具，不依赖系统 `/usr/bin` 版本。

## 已核实的接入缺口

| 当前实现证据 | 真实程序的需求 | 接入工作 |
| --- | --- | --- |
| `language_adapters.py` 的 C 适配器面向固定 uint32 布局 | 字节字段、变长行、多个缓冲区 | 将 ABI 参数解码与通用字节区域/版本记录分开，复用依赖图而非硬套原布局 |
| `interproc_model.py` 受限于 32/64 位操作、已知区域和直接调用 | 字节读写、动态地址、库调用及优化指令 | 对固定 ELF 做指令和调用清单；未知形式拒绝，不能跳过 |
| `byte_provenance.py`/`go_byte_adapter.py` 已有字节核心，但入口仍绑定四字节叶函数及 Go 边界 | 原始 C 程序的变长区域和跨函数传播 | 不能把“存在字节核心”当作已具备完整 C 字节分析 |
| `read_boundaries.py` 验证的是预先打开文件的受限 pread64 | fopen/read、stdio 预读、ungetc、缓冲复制与复用 | 显式记录读取版本和缓冲流转，不按数值补来源 |
| C/libdft64 适配器在三个指定根函数入口打标签 | 文件读取返回到实际 stdout 写出 | 新的 read/write 边界适配；保留原版 libdft 传播，不使用查询答案代替传播 |

源码核查：`cut_fields` 涉及 getc/ungetc、getndelim2、fwrite、putchar 和可重用首字段缓冲；`join` 使用动态行/字段结构、键匹配及 prfield/prjoin 输出。不能通过给 cut/join 手写“第几列来自第几列”的函数摘要绕过待测算法。

目前没有证据表明现有 uint32 运行器能够直接对这些程序产生正确来源结果。接入工作完成之前不发起正式性能实验，不把不支持记录为零开销，不删除失败用例以提高准确率。

## 接下来的实施门槛

1. 构建固定原始源码，生成完整函数/库调用/指令清单。先接 cut，join 保留在预注册集合中；失败仍记录。
2. 建立双方共用的文件字段来源和 stdout 字节目标边界，验证缓冲与读写版本，独立核验库摘要或显式跟踪库内传播。
3. 分别运行我们的全观测与选择性观测、原版 libdft64。统一查询、输入、ELF、依赖语义及分析范围；全程序基线成本与局部路径成本分列。
4. 核对完整来源集合、TP/FP/FN、unknown 和无输出结果。功能预检只占准备阶段，不计入这些指标。
5. 来源正确性通过后，再用同负载、预热、重复与记录的顺序测业务 CPU/延迟、采集 CPU/内存、离线分析 CPU/时间/内存；静态分析与挂接单列。既有微型诊断结果不与真实程序性能拼表。

这些工具主要补字段选择、缓冲和多记录身份方面的真实代码复杂度；金额算术证据仍由原始 checkout 实验提供，不将不同实验拼成一个不存在的全程序能力声明。
