# 同一 Item/Cost 查询下的观测策略比较

本轮固定两个目标：最终 Item 的输入对象候选集合，以及最终 Cost 的成功转换返回实例候选集合。比较探针策略对这两个查询的正确性、事件量与运行开销的影响，不继续扩字段或语言。

## 四组设置

| 名称 | 本地目标探针位置数 | 观测范围 | 用途 |
|---|---:|---|---|
| native | 0 | 不启用 BPF；测试夹具仍保留独立真值 | 耗时基线，没有观察者溯源结果 |
| boundaries | 7 | 订单入口、转换调用前后、切片发布后、订单返回 | 按已声明查询证据规则自动生成的精简策略 |
| current | 11 | boundaries 加候选 Item/Cost 偏移写入操作数 | 前一版已经通过主机验证的采集策略 |
| dense_stores | 37 | current 加当前函数内可达的 `MOVQ` 寄存器到内存写入，包括栈保存和写屏障写入 | 更密集的局部观测对照 |

位置数由实际目标 ELF 生成，不是硬编码。重复地址只挂一个探针；密集组包含原查询所需的全部探针。密集组额外记录写入地址和源寄存器值，不跟进被调函数内部，不覆盖其他宽度/SIMD 写入，也不重建每条指令的污点传播。

**这是一组系统内部的观测消融，不是对 HardTaint、SelectiveTaint、FlowDist 或完整动态污点系统的复现比较。** 精简策略现在从声明的证据依赖图生成，并非自动推导出的最优探针集合；不能据此声称提出了新的最小观测算法。查询语义、观测语义和适配器边界仍显式配置，见 [SELECTION.md](SELECTION.md)。

三种策略评估的是相同的最终引用身份候选集合。精简组不再要求字段赋值指令前的操作数见证；当前组和密集组仍保留该一致性检查。因此，三组在“识别中间操作数冲突”方面的证据强度不同，不能把身份查询一致解释为完整写入历史同样可观测。

## 运行

在仓库根目录、此前可运行 BCC 的主机上执行：

```bash
git pull --ff-only
sudo env "PATH=$PATH" GOPROXY=https://goproxy.cn,direct \
  /usr/bin/python3 experiments/checkout-item-identity/run.py compare
```

仍要求 Go 1.25.4；原有 `--go`、`--checkout` 和 `--output` 参数可用。不需要 Docker。

默认流程：

1. 构建同一个正常优化的测试二进制，生成三份探针计划。
2. 七个场景分别运行三种 BPF 策略，共 21 次正确性验证。每次推断完成后才读取该次独立真值；采集不完整或不一致即停止，避免为错误结果报告开销。
3. 只针对 32 商品场景做性能比较：1 轮预热、5 轮计入统计。每轮 native 与三个 BPF 策略各执行一次，轮内顺序按固定种子打乱。
4. 写入 `comparison.json`、原始 `trials.jsonl`、执行顺序和全部采集资料，并打印结果 zip 路径。

总计 45 次目标进程运行，其中 39 次加载 BPF。每次都是独立进程、一次订单调用；脚本打印进度，比此前七场景验证耗时更长。支持 `--repeats 10 --warmups 2 --seed 123` 调整重复次数；至少 3 轮测量。预热也是新进程，只减少运行顺序/宿主缓存等启动效应，不声称目标进程内部已完成 JIT 或业务预热。

不需要删除旧结果。执行失败仍会归档已完成的日志、采集和试验记录；此前 `run` 模式继续可用。

## 计时与统计口径

- **目标调用耗时**：测试夹具在原始 `prepOrderItems` 前后用 Go 单调时钟计时。开始前等待本机 gRPC 连接 Ready；包括本次订单循环、局部 RPC、调度和测试真值拦截器成本。排除 BPF 编译/挂载、真值 JSON 序列化及写文件。原应用业务源码不改。
- **共同基线条件**：同一二进制、测试拦截器和 mock 后端，native 也保留同样的计时与断言。每次只处理一个订单，没有并发请求/吞吐量结论。这里不是没有测试夹具的生产部署测量。
- **开销比例**：每轮某策略的调用耗时除以同轮 native 耗时，保留所有比例，报告其中位数与百分比增量；同时报告各策略的耗时中位数、最小值和最大值。允许出现负增量，不截断成零。
- **事件量**：实际成功解码事件数及内核计数一致性检查。探针位置数与运行事件数分开报告。
- **数据量**：各 perf 回调 `size × count` 之和；另记录逻辑事件字节量。所有策略使用相同 840 字节事件结构（已验证 BCC 回调常为 844 字节），未按事件种类压缩。这不是网络带宽、全部 perf 内存占用或生产最优编码大小。
- **推断耗时**：单独记录 Python 对已解码事件进行推断的时间，排除真值比较、BPF 编译与 JSON 文件读写；不与应用调用耗时相加。
- **正确性**：每个 BPF 策略应通过七个场景、88 条最终字段引用关系的候选集合比较，包含 Item 的两个别名歧义输出。两个失败场景最终输出为空，但仍检查调用状态、输入和转换边界真值。

结果包含每次原始测量，便于检查波动。默认五次重复只用于探索，不能据此宣称统计显著、通用低开销或比现有完整污点方案更优。减少无关探针本身也不自动构成方法创新。

## 已完成的主机比较

归档 `checkout-item-identity-20261009-012806-045492.zip` 已逐项核对。三种策略各通过七个场景、88 条最终引用关系。39 次 BPF 采集的完整性、原始事件推断及独立真值均一致；计划对应的 ELF 哈希和指令字节通过检查，20 条测量记录重新计算后与报告一致。

| 策略 | 32 商品事件中位数 | 调用耗时中位数 | 五次耗时范围 |
|---|---:|---:|---:|
| native | 0 | 29.68 ms | 28.73–31.53 ms |
| boundaries | 98 | 32.74 ms | 30.57–34.25 ms |
| current | 226 | 33.51 ms | 33.17–36.06 ms |
| dense_stores | 427 | 33.79 ms | 32.99–35.81 ms |

精简组比当前组少 56.6% 事件，耗时中位数降低约 2.3%。这些是**中位数之比**；原始 `comparison.json` 另报同轮 native 配对比值的中位数，两种统计不能混用。五轮中有一轮精简组慢于当前/密集组，尚不能声称稳定或统计显著的性能优势。

记录中 `reference_relations_matched` 指这两个已限定查询的候选集合比较，不是任意字段溯源准确率。密集组也不是完整动态污点基线。

## 本地验证与后续规则化

- 本地正常构建及三份探针计划通过检查，位置数为 7 / 11 / 37；七个原生夹具场景通过，native 计时读取已验证。
- 30 项单元测试覆盖策略裁剪、地址去重、缺失必要事件拒绝、候选集合保持、打乱调度、预热排除和配对统计。
- 旧版 v1/v2 的 14 个真实采集场景离线回放保持一致。
- 对已上传的 v2 事件做**离线过滤试验**：删去字段操作数事件后，七个场景仍得到同样的身份结果，事件从 342 条变为 154 条。这不是精简探针主机采集，也不是耗时收益；实际效果须运行 `compare` 确认。
- 精简组和密集组的真实 BPF 验证已完成，结果见上表。计时夹具预先连接 gRPC，这些测量不能与更早的不同计时口径混用。
- 自动查询裁剪生成的默认计划与上述精简组地址/顺序相同；13 份已运行 BPF C 程序逐字一致，39 次采集的查询结果经回放/明确标记的离线投影后仍与真值相符。自动规则化不会使已有性能结果变成新的独立实验。

```bash

```
