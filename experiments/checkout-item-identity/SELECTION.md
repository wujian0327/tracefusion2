# 从查询所需证据推导观测位置

之前 `boundaries` 的实现直接删除所有 `field_operand` 类型探针。现在改为：**给定查询、观测能提供的事实，以及派生事实的依赖规则，计算依赖闭包，保留所需事实的全部产生位置。**

这一步是可检查的规则化。它没有自动理解任意程序语义，也没有证明全局最小观测集合；当前的新自动化环节是“声明证据模型之后如何生成探针子集”。

## 分层

- `scripts/observation_selection.py`：与 Go/eBPF 无关的依赖闭包核心。输入事实产生位置、合取依赖规则、查询和上下文，输出位置集合、推导步骤和逐位置理由。
- `selection_rules.py`：当前 checkout 对象身份查询的证据语义。入口/返回、发布、转换边界及字段操作数能提供哪些事实由此声明。
- `observer.py`：已有二进制/CFG/DWARF 适配器继续定位真实地址，调用规则核心生成精简方案，并在生成 BPF、运行离线推断前校验选择记录。
- `audit_selection.py`：在旧比较归档上复核自动计划、指令字节、原始推断、投影结果和采集程序一致性，不重新运行 BPF。

## 当前规则

| 查询或派生事实 | 必需证据 |
|---|---|
| 执行范围 | 订单入口和所有可能的订单返回位置 |
| 转换调用实例 | 转换入口、转换返回、执行范围 |
| `identity.Item` | 输入 Item 对象集合、发布时 Item、最终 Item、执行范围 |
| `identity.Cost` | 转换调用实例、发布时 Cost、最终 Cost、执行范围 |
| 可选的操作数一致性检查 | Item/Cost 写入前操作数、发布时 Item/Cost、执行范围 |

Item/Cost 查询指在已观测边界上相同活对象的身份关系。Cost 候选只包含发布之前已成功返回的转换实例。字段操作数对这两个身份查询不是必需叶事实，但它是“检查候选赋值操作数与发布快照是否一致”这一附加诊断的必需证据；增加该诊断目标会自动把相关位置加回来。

事实语义、上述推理依赖及 ABI 是显式配置，不是从二进制自动发现的完整业务语义。现有二进制分析负责找到对应指令位置、全部静态可达返回和独占后继；两层职责不能混淆。

## 算法与条件

记查询集合为 Q，规则 `f <- d1,...,dn` 表示派生事实 f 必须同时获得全部依赖。核心从 Q 反向访问规则，直到直接观测事实，遇到不存在的事实或循环依赖即拒绝。设叶事实集合为 L，每个事实的产生位置集合为 P(f)，保留集合为：

```text
S = union(P(f) for f in L)
```

**P(f) 中的全部位置都要保留。** 例如三个 RET 都产生“最终输出快照”，它们可能属于不同执行分支；不能因为任意一个 RET 都具有这个标签就只选一个。这里没有做把分支当冗余副本的集合覆盖优化，也不依据某次执行没有触发某个位置而删除它。

在声明的模型内，查询需要的叶事实都保留了其产生位置。该条件只说明模型内的证据覆盖；要获得程序级正确性，还依赖：

1. 适配器识别的作用域、候选位置和观测语义确实正确且足够完整。
2. 活对象地址在本次受控生命周期内稳定；不能把可能回收复用的地址当永久身份。
3. 保留探针实际成功挂载，读取、提交和丢失检查通过，入口/返回配对与 PID/goroutine 关联有效。
4. 所问的是当前身份查询，不是内部数值加工、完整写入历史、远端计算或隐式控制依赖。

核验记录保留了这些前提，并绑定二进制哈希、ABI、字段布局、完整候选目录及规则。改变目录、查询、所选地址或丢掉某个必需位置都会使重新计算的记录不一致。该记录是**模型内的选择审计记录，不是形式化程序语义证明或防篡改安全凭证**。

未声明的事件类型会使适配器拒绝生成自动计划。不存在证据规则的 `full_write_history`、`numeric_dependency` 等查询也被拒绝，不沿用七点计划声称支持。

## 在当前 ELF 上的结果

| 目标 | 自动保留的位置数 | 状态 |
|---|---:|---|
| 只规划 Item 身份查询 | 5 | 仅规划测试，现有执行器不支持单独执行此查询 |
| Item + Cost 身份查询 | 7 | 与已在主机运行的精简组计划相同 |
| Item + Cost + 操作数一致性检查 | 11 | 保留原方案的附加检查，单元测试覆盖冲突拒绝 |

从 11 点原目录或 37 点密集目录出发，默认身份查询都生成同样的七个位置。位置数是本次目标与模型的结果，不在选择核心中写死。`run.py build/compare` 现在额外保存 `selection-boundaries.json`，逐点展示保留事实或删除理由。

## 验证结果

- 39 项单元测试通过，覆盖多返回分支、模型缺项、未知查询、闭包循环、目录/地址变更、逐个删除必需位置、查询增加诊断后自动恢复操作数观测等情况。
- 使用既有比较归档回放全部 39 次 BPF 采集，默认查询结果与独立真值一致。其中 26 次 current/dense 记录先校验完整原始采集，再做明确标记的离线投影；不是声称这些进程当时运行了七点方案。
- 对 13 次真正使用精简方案的主机采集，自动计划生成的 BPF C 源码与归档中的 `collector.c` 逐字一致，探针地址/顺序和二进制字节也一致。
- 本次无需再进行相同主机采集来验证这七个地址；没有新增独立性能测量。

可选的本地复核命令（不需要 sudo、BCC 或重新编译 Go）：

```bash
python3 experiments/checkout-item-identity/audit_selection.py \
  artifacts/checkout-item-identity-20261009-012806-045492.zip
```

脚本在 `artifacts/selection-audit-时间/` 保存三个查询计划与 `audit.json`。完整默认自动计划附有证据依赖记录；单独 Item 查询的五点计划只作为规划结果保存，执行校验会明确拒绝。

目前仍不能据此宣称一个通用的新选择算法。接下来的研究问题是：当查询确实需要动态分支、覆盖或内存别名证据时，如何从分析结果中得到可靠的证据依赖，而不把关键语义继续交给手工配置。
