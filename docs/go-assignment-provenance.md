# 来源集合与同值覆盖验证

当前研究目标收敛为：维护输出对象的实际来源集合，正确处理传播、合并与覆盖。不要求用户分析每个字节的加工过程。本实验复用已有内存写入模型，验证同值覆盖后旧来源能否清除。

## 运行

沿用 Linux amd64、Go 1.25.4/1.25.5、系统 Python 和 BCC 环境：

```bash
cd ~/tracefusion2
git pull --ff-only
sudo env "PATH=$PATH" /usr/bin/python3 scripts/go_byte_provenance.py run --suite assignment
```

脚本编译三个目标并执行六个用例。运行成功或失败均打印 `Return this archive: ...zip`，请返回该 ZIP。只编译和规划使用 `build --suite assignment`。原来的正序/反序加工测试保留为 `--suite instruction`，也是未指定 suite 时的默认值。

## 场景

A、B、C 来自三次独立读取，内容均为 `SAME`。请求选择 A 或 C 作为第一份输入，B 是第二份输入。所有数组均为四字节，各自具有独立存储。三个目标复用同一个主程序和函数 ABI：

- `assign.go`：将选中的 A/C 写入输出缓冲区。
- `partial.go`：先将选中的 A/C 写入输出，再用 B 覆盖前两个位置，随后直接输出。
- `overwrite.go`：先将选中的 A/C 写入输出，再用 B 完整覆盖同一个缓冲区。

三个目标中的赋值均由简单循环实现，没有增加截取、编码或其他加工类型，也没有给覆盖函数配置“最终来自 B”的摘要。分析器根据实际执行的读写指令更新各存储位置的定义，再汇总为输出对象的来源集合。

| 用例 | 输出 | 最终来源 | 应清除的曾写入来源 |
| --- | --- | --- | --- |
| `assign_a` | `SAME` | A | 无 |
| `assign_c` | `SAME` | C | 无 |
| `partial_a` | `SAME` | A、B | 无 |
| `partial_c` | `SAME` | B、C | 无 |
| `overwrite_a` | `SAME` | B | A |
| `overwrite_c` | `SAME` | B | C |

既不能因为 A、B 值相同而将其当作一个来源，也不能把所有历史上写入过的来源永久并入输出。

## 输出与正确性

`<用例>/inference.json` 的主要结果是：

- `sources`：最终输出仍依赖的来源实例。
- `overwritten_sources`：曾经写入输出，但被后续写入完全替换的来源。
- `source_versions`：输出缓冲区已有完整定义后，来源集合发生变化的时点。
- `total_writes`：内部观测到的存储次数，用于确认两轮写入确实执行。

覆盖由多条存储指令完成，因此 `overwrite_a` 的来源变化应为 `{A}` → `{A,B}` → `{B}`。中间状态表示部分位置尚未被 B 覆盖，不应提前删除 A；完整覆盖后也不应保留 A。三个阶段的完整缓冲区内容都是 `SAME`。`overwrite_c` 同理。`partial_a` 则在 `{A,B}` 状态直接输出：最后两个位置仍来自 A，不能因为发生过 B 的写入就提前清除 A；`partial_c` 同理。

内部继续使用现有字节单元与逐次指令定义，避免部分覆盖误删来源；`byte_sources` 作为诊断证据保留。但 assignment 套件的真值和通过条件以来源集合、来源变化、旧来源清除及输出正确性为主，不提供或要求逐字节对应关系。`source_relations` 报告来源级 TP/FP/FN、precision/recall。

推断器不读取请求选择、用例名或 oracle。source 仍是一笔读取调用及其返回数组。B 的指针由 Go ABI 第三个参数寄存器采集，绑定到已观测读取；加载 B 时再用实际内存字节验证此前定义。读取和 JSON 边界模型仍有配置。

除原六个证据破坏检查外，本套件删除一次最后阶段的写入事件，要求返回 `unknown`。这个检查验证当前观测契约下的事件缺失，不代表可以发现任意未观测写入。

## 实现与验证范围

主要复用 `byte_provenance.py` 的存储覆盖规则：新写入替换对应位置的旧定义，不对历次来源简单累加。第二输入区域的 ABI 绑定和对象级来源变化报告沿用上一版；新增部分覆盖用例没有修改推断核心或采集器。采集事件布局、BCC transport 和现有指令语义均未扩展。

本地 Go 1.25.4 构建保留了两轮循环：赋值目标有 10 条静态指令，执行 33 步；部分覆盖目标有 19 条静态指令，执行 51 步；完整覆盖目标有 19 条静态指令，执行 65 步。加上各 10 条边界事件，预期每个赋值用例 43 条、部分覆盖用例 61 条、完整覆盖用例 75 条，六例共 358 条。仍应检查事件内容与推断，不能只看计数。

### 已完成的主机验证

用户返回的 `go-byte-provenance-20261004-125503-994505.zip` 包含上一版赋值与完整覆盖四个用例。在 WSL2、Go 1.25.4、BCC 0.29.1 环境采集 236 条事件，没有报告丢失、读取或提交错误。已校验归档二进制和源码哈希，重放原始事件，核对来源读取地址、两轮写入地址及最终输出。四个来源集合均正确，完整覆盖后的依赖图不含旧来源。七项离线证据破坏检查均返回 `unknown`；这些是修改已采集事件的负向检查，不是七次额外内核实验。

### 本次新增验证

三个目标编译、六次直接执行均通过（全部输出 `SAME`），10 项指令/赋值测试和 15 项字符串测试通过。独立事件夹具验证部分覆盖保留两个来源，评分器会拒绝提前删除旧来源。部分覆盖的真实 eBPF 采集尚待主机验证；本地编译与合成事件测试不能替代它。

### 本轮结束标准

收到六例主机结果后，检查最终来源、完整/部分覆盖对照、事件完整性及负向检查。如果通过，冻结这组基础测试，仅作为后续回归使用，不再持续添加加工类型。下一阶段验证 Go → Go 双服务 API 的读取、传输、合并与输出来源衔接；跨服务真值和性能开销需单独设计，当前结果不作为其通过依据。

当前仍是单请求、单 goroutine、独立输入区域与输出缓冲区、受限叶函数指令集合。没有新增并发写入、输入输出别名、跨服务传播或通用对象布局支持。输出只表达显式数据来源，不表达访问权限、法律权属或控制依赖。内存细粒度记录是当前实现手段，逐字节加工还原不再作为本套件的研究目标。
