## Java 服务的明确缺口

- 上游 build.gradle 指定 Java 19 target，当前独立解码器最高接受 Java 17 class。
  本地已准备的对照 JDK 也是 17。降低上游 target 不能悄悄算作原始构建支持。
- `getAds`、`getAdsByCategory` 是实例方法；采集器和解码器要求静态方法。
- 服务使用引用字段、字符串、Guava 集合、protobuf builder 和跨类调用；
  当前字段观测只覆盖非 volatile int 字段，调用范围也受限。
- `getAds` 有异常处理，当前引擎拒绝；多线程 RPC 需要实际验证和请求状态隔离，
  不能根据源码断言已经观察到线程迁移。
- 空类别/无匹配类别触发随机广告，需要额外运行证据；不能靠输出内容猜随机选中的来源。
- 广告内容来自预置目录，关键词影响选择。若只问请求关键词到正文的直接数据依赖，
  大量空集合答案不足以证明复杂字段来源恢复。

上游 Dockerfile 用 JDK21 构建、JRE25 运行；固定 Galette README 声明运行时支持 8–21。
JDK21 是后续共同运行环境候选，需要重新准备和实际验证；改变部署运行时必须披露。
既不能把当前 JDK17 对照直接用于 Java19 class，也不能断言 Galette 已支持此服务的 JRE25 部署。

这说明从当前整数/数组原型到原始服务需要实质扩展，不是换一条运行命令。
adservice 保留为字段选择/转发候选，不能单独承担复杂算术来源或通用 Java 服务支持的结论。

现有正确性结果直接复用；变更影响的核心语义和新增路径再做定向验证。

## 准确性报告口径

每个程序预先登记独立真值、来源边界、目标、版本、支持范围和输入。
字段区分、同值异源、加工/合并、选择/覆盖、实例隔离是共同检查维度，按原始行为选输入。
独立真值不得由被比较的 full 模式或外部标签单独决定。

分两张表：

- 多语言正确性表：程序/查询、有效查询数、完全正确数、错误数、unknown/失败、已覆盖行为。
- 同任务外部表：共同支持范围内的集合正确率、TP/FP/FN、Precision/Recall，以及语义差异。

重复调用和多模式运行不增加独立程序或输入数；no_sink、空来源、未知和不支持单列。
四种语言分别能运行，与实际跨语言服务调用链来源恢复，是两项不同证据。
完整资源和运行协议沿用 [实验设计](experiment-design-20261012.md)。

## 当前字段级主评价口径

[cJSON 字段评分](../experiments/cjson-provenance/FIELD-RESULTS.md) 以源字段实例到目标字段实例为关系，
使用源码推导标注，比较同粒度的显式内容来源集合。报告微平均 Precision/Recall、查询集合完全匹配率及覆盖比例，
单列范围外、unknown、无目标与运行失败。底层字节标签一致性用于校准，不能替代字段真值或逐字节真值。
跨语言主表只比较已统一的关系语义；工具支持范围的差异保留，不能用投影掩盖。
