# 实际 gRPC 客户端的接收者访问摘要

日期：2026-10-08。继续检查被调函数的内存影响；不是 BPF 验收，也没有解除已有的未知栈标记。

## 这次具体分析什么

此前已分析业务函数 `prepOrderItems` 和 `convertCurrency`，但把下层调用视作未知。本轮继续读取同一默认优化 ELF 中实际被调用的两个生成客户端方法：

- `genproto.(*productCatalogServiceClient).GetProduct`
- `genproto.(*currencyServiceClient).Convert`

这里的“接收者”是方法的 `c`，即临时客户端对象；不是商品对象、币种返回对象，也不是远端服务。Go amd64 方法调用中它位于 AX。配置给分析器的是该 ABI 根位置，不是“此函数不会写”的业务答案。

每个方法完整反汇编 101 条指令，与原 ELF 全符号范围及逐条机器码核对。建立栈帧后的主体均为 79 条指令，帧大小 128 字节。目标 ELF 仍是 SHA256 `d5668e6bce805073aab2f452f821745d7e0a2944ff20f52d2e0ad549f379409f`，应用源码未参与本轮分析。

## 提取结果

| 检查 | GetProduct / Convert 的结果 | 可以怎样解释 |
| --- | --- | --- |
| 经原接收者地址读取 | 偏移 0 和 8，各 8 字节 | 两个字段的读取范围明确 |
| 经原接收者地址直接写入 | 未发现 | 只描述本摘要追踪到的直接地址流 |
| 原接收者地址外传/返回 | 未发现 | 未直接传入后续调用、写入外部内存或返回寄存器 |
| 接收者字段里的值 | 进入后续间接调用 | 不能把“原地址未外传”当作完整无副作用证明 |
| 间接调用目标 | 先读取接收者 `+0`，再读取所指对象 `+24` | 自动得到指针加载链 `[0, 24]`，尚未解析为实际目标函数 |
| 该调用 AX 参数 | 读取接收者 `+8` | 自动得到另一条加载链 `[8]` |

这是条件化的相对访问摘要。若某个已加载字段恰好指回接收者或调用者栈，下游依然可能经该别名写入；其它参数也可能提供另一条访问路径。因此以下字段始终为 false：

```json
{
  "transitive_no_write_proved": false,
  "may_preserve_caller_spills": false
}
```

**没有将这两个客户端方法加入免失效白名单。**主图仍使用上一阶段的保守规则。商品对象保存槽及结果切片地址上的未知仍然存在。

## 算法及边界

新增 `scripts/go_receiver_summary.py`，复用有限定义图并对接收者根做标记传播。精确复制保留标记；从接收者加载的值使用另一种标记，区分“对象本身的地址”与“对象中保存的值”。控制流合流与循环采用有限集合不动点，不根据源文件行号或方法名称返回结论。

检查直接写入、通过调用寄存器/潜在栈参数外传、间接存储发布、返回、被用作间接调用目标。局部栈地址暴露、经该别名的写入以及当前不处理的接收者指针运算，会使摘要拒绝。潜在栈参数按帧内保存位置作保守近似，可能多报外传，不声称精确恢复所有调用签名。

该局部检查仍依赖正常 Go ABI、编译器栈布局和无隐藏局部栈别名等条件；这些条件列入报告，没有自动证明全调用链满足它们。加载值是否别名回接收者、其它参数的别名、下游未知调用的内存影响都保留为义务，不将条件化直接访问检查宣传成完整只读证明。

为读取真实产物，图解析增加了负立即数 ADD 建帧形式、相应整数指令以及显式开启的寄存器间接调用解析。普通对象分析默认仍拒绝间接调用；只有摘要检查启用解析，且将目标及其来源链明确列出。解析成功不表示支持任意接口调用的动态溯源。

## 验证

新增 13 项摘要测试通过，覆盖实际两个客户端以及直接写入、原地址外传、栈保存后重载外传、潜在栈参数外传、外部存储发布、后续 ABI 返回寄存器、间接调用目标、未建模指针运算、暴露局部栈地址、未知指令和默认拒绝间接调用。加上既有 26 项，共 39 项通过。

摘要测试确认“字段值外传”不能使 `may_preserve_caller_spills` 变为 true。真实产物 CLI 检查重新执行，未修改原始 ELF。汇总与函数代码哈希见 [本地记录](checkout-receiver-summary-local.json)，回归汇编来源记录位于 `tests/fixtures/checkout-object-graph-origin.json`。

同一个 `analyze_binary.py` 命令现在输出 schema 3，新增 `callee_summaries`，保留原有保守主图和 unknown。没有新增主机运行任务。

## 下一项证据

检查调用者怎样构造这个临时对象，绑定其两个字段和其它传入参数的实际来源；再判断是否存在指回目标保存槽的路径。只有在当前声明的 ABI/内存模型下补齐隔离证据，或取得相关写入的运行证据后，才能恢复来源边。还不能仅凭接收者字段值相同就解除未知。
