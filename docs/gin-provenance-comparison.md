# 来源观测策略的公平对比

本轮不扩展来源核心、Go 指令集或运行时能力。固定现有四字节复制、单个不可变私有控制字节、两个 Gin 服务和 OTel 边界，检验已有方法能否取得与当前自动策略相同的观测节省。

## 本地结果及含义

五种真实 Go 1.25.4 构建中，独立路径敏感基线与当前策略生成的**探针位置及快照内容完全相同**。独立 Unicorn 指令执行、来源检查及五组真实 HTTP/OTel 测试通过。新增场景的两处条件分支保留在机器码中，没有被编译器化为无条件复制。

具体二进制身份与验证范围见 [本地验证记录](gin-provenance-comparison-local.json)。相关套件 33 项，30 项通过、3 项旧构建集成测试因未设置对应环境路径跳过；本轮新增的五场景原生集成检查已执行通过。

| 场景 | 来源集合基线 | 路径敏感基线 | 当前 auto |
| --- | --- | --- | --- |
| kill-full：最终无条件完整覆盖 | output | output | output |
| kill-partial：仅最后两字节覆盖 | entry | entry | entry |
| kill-none：没有后续覆盖 | entry | entry | entry |
| correlated：选择本地时才用上游字段纠正 | entry | output | output |
| correlated-dependent：只反转第二个条件 | entry | entry | entry |

`output` 保留边界、不记录叶函数内部事件，只回答最终来源；`entry` 另外记录一个控制初值，重放受支持的执行。模式名称均沿用现有系统。

这支持一个明确的负结果：**在这些场景里，当前方法未比普通路径敏感推导进一步减少观测。**它不能证明更广范围没有研究空间，也不能作为优于 HardTaint 等原始系统的结果。内核 eBPF 实际采集仍待主机运行；本地机器码模拟事件不冒充内核采集。

## 基线具体做什么

`scripts/provenance_baselines.py` 独立消费二进制解码的 IR，不读取场景名、预期答案、真实输入字节或当前输出证明的分析结果。

- **origin_sets**：非关系型来源集合分析。展开有界循环，在合流点合并可能来源，每次输出写入强更新旧定义。对于未知条件分别考虑两条边，但不记住不同判断之间的关联。它是常见分析能力的方法控制，不是完整通用后向切片器。
- **path_sensitive**：独立解释器保留同一控制值在不同分支之间的关联。限定仅有零/非零比较，因此分别执行这两个输入类；逐字节比较最终来源。它包含了增强基线应有的推导能力，不刻意让基线逐条采集。
- **enumerate256**：测试用独立穷举检查，遍历全部 256 个初值验证两类分区；不将它当成故意缓慢的性能基线。
- **auto**：冻结使用当前 `choose_observation`。
- **full**：完整记录下游受支持叶函数指令，配合独立场景真值检查最终来源。

所有组使用相同的二进制、源内容、请求负载和采集/绑定代码。上游在**全部方法中固定为 boundary**，避免把上游优化的收益算到新的下游方法上。推导基线与当前策略都能选择 output 或 entry；full 作为完整证据参照。

基线的观测选择独立完成后，复用现有计划适配器与运行时验证器。选择 output 时，公共验证器重算输出证书并核对基线给出的来源投影；两者冲突立即失败，不会悄悄采用当前策略的答案。因此独立的是选择分析，不是整套端到端系统。

`decision_ns` 记录选择分析时间，`planning_with_shared_validation_ns` 还包括公共验证开销。解释器实现、语言开销和微型程序限制使这些数字不适合作为通用静态分析性能结论。

## 关联分支场景

`correlated.go` 的实际逻辑为：

```text
第一轮：条件为零，从上游复制；否则，从本地复制。
第二轮：仅当条件非零时，重新从上游复制。
```

由于控制字节在调用内不变，输出始终来自上游，但两类执行的中间写历史不同。非关系型分析允许“第一轮非零、第二轮为零”的不可能组合，保留了本地来源；路径敏感分析可以排除这个组合。

`correlated-dependent.go` 只将第二轮条件改为零，此时初始本地来源会保留，必须观测控制值。所有正式采集仍使用内容相同的 `SAME`，不能凭值相同合并来源。原生 HTTP 测试另将本地内容设置为 `LOCL`，独立检查路由与最终输出。

这不是循环中新到达的 I/O，也不支持未知外部写入。边界、对象不重叠、请求私有性、完整受支持指令模型仍是已有约束。本轮不宣称解决通用别名、共享状态或任意字段。

## 主机执行

先运行两组新增场景即可；它们是本轮最有区分力的用例：

```bash
cd ~/tracefusion2
git pull --ff-only
sudo env "PATH=$PATH" GOPROXY=https://goproxy.cn,direct \
  /usr/bin/python3 scripts/gin_provenance_comparison.py run \
  --variant correlated --variant correlated-dependent
```

共两组 × 四种方法，每次八个外部请求，沿用现有 Go 1.25.4、BCC、Gin 和 OTel 环境。方法执行顺序按记录下来的固定种子打乱。返回最后打印的 `artifacts/gin-provenance-comparison-*.zip`，失败也返回。归档包含原始事件、二进制身份、计划、证书、HTTP 响应和 span，重复二进制使用 `binary-aliases.json` 记录。

不启动 BPF 的完整构建/策略检查：

```bash
python3 scripts/gin_provenance_comparison.py build
```

省略 `--variant` 会运行全部五组。`--repeats 3` 可用于后续重复采样，目前无需先做大量性能运行。

## 查看什么结果

- `static-comparison.json`：基线与 auto 的探针是否相同；其中 `host_capture_complete` 为 false，不能当作 BPF 成功。
- `decisions.json`：每个独立分析的来源集合/决策、耗时以及探针签名。
- `comparison.json`：采集完成后，各方法的最终逐字节来源是否与 full 一致，以及 auto 相比路径敏感基线究竟少了多少事件；没有节省就如实记录 0。
- `measurements.json`：完整性计数、事件数、探针数、紧凑 JSON 事件大小、八请求延迟样本、来源正确与 unknown 计数。
- 各次 `evaluation.json`：按请求和字段检查来源，并运行缺失观测、错误对象/上下文等负例。任何错误归因、必要事件缺失或采集失败都会使试验失败，保留原始证据，而不是用失败请求美化开销。

延迟是短并发夹具的端到端耗时，包含应用等待、HTTP 和 OTel 成本。事件 JSON 字节数不是内核传输字节数；八个请求的 p95 接近最大值。这里不计算“生产性能提升”，也不以不同运行的少量延迟波动推翻相同探针的事实。

所有方法提前知道目标输出字段。比较的是最终来源身份与字节偏移，不是唯一中间路径、隐式控制流泄露或事后任意输出查询。
