# 双 Gin：控制输入的观测位置与重复使用条件

前一轮主机实验说明：在输入完整、内部执行可确定的四字节叶函数中，可以删去内部指令探针。本轮检验相反情况：**现有边界快照没有覆盖一个决定数据来源的运行时输入时，必须保留歧义；补充该输入的观测后才能重建本次实际来源。**

## 场景与预期

继续使用两个 Gin 服务、真实 OTel SDK、相同的读取/JSON/HTTP 边界和请求作用域隔离。上游仍在 A/C 中选择。下游读取上游结果与本地 B，循环写入四字节输出：

```go
for i := 0; i < 4; i++ {
    if *control == 0 { dst[i] = src[i] } else { dst[i] = other[i] }
}
```

`control` 是独立的一字节对象，由下游 `readControl` 根据请求 query 创建。编译后的 transform 第四个参数寄存器 DI 保存它的地址；原有 work-entry 快照只读取 src/dst 的四字节内容，没有读取 control 的内存内容。所有数据源仍为 `SAME`，两条分支的输出相同。

| 模式 | 内部观测 | 预期结果 |
| --- | --- | --- |
| full | 采集所有已建模指令，包括控制字节比较 | 8 个请求均解析到实际来源 |
| boundary | 不采集内部指令，不补 control 内容 | 下游 8 个请求均 unknown，明确缺少运行时输入观测 |
| selective | 下游只保留 control 比较的一个指令位置 | 8 个请求均解析，逐字节来源与 full 一致 |
| entry | 在 transform 第一条指令执行前读取一次 control | 通过稳定性检查后，8 个请求均解析，逐字节来源与 full/selective 一致 |

单个比较位置在循环中执行四次，因此 selective 在下游每请求保留四条内部事件；entry 每请求只保留一条入口输入事件。两者都挂载一个位置，但位置与触发次数不同。上游没有这种额外输入，可继续零内部探针重放。四种模式复制同一组二进制；不通过改写程序为不同采集模式制造差异。

前三种模式已在主机通过：full 共 976 条事件，boundary 336 条并正确保留 unknown，selective 368 条且来源与 full 一致。新增 entry 的真实 BCC 采集仍待验证；按当前场景预计保留 344 条事件，**该数字是预期，不是已测结果**。

测试客户端安排 ticket 2/3/6/7 使用本地 B，1/4/5/8 使用上游结果，同时独立交替选择上游 A/C。这些规则只用于评价，不进入来源推断。

## 运行

环境沿用上一轮：Linux amd64、Go 1.25.4、Gin 1.11.0、系统 Python/BCC。

```bash
cd ~/tracefusion2
git pull --ff-only
sudo env "PATH=$PATH" GOPROXY=https://goproxy.cn,direct \
  /usr/bin/python3 scripts/gin_choice_provenance.py run
```

返回打印的 `artifacts/gin-choice-provenance-*.zip`，失败也返回。boundary 的 unknown 是本实验的正确结果；缺失事件、采集错误、错误的 unknown 原因仍会导致实验失败。

更新后同一命令会依次运行 full、boundary、selective、entry 四种模式。

只构建：`python3 scripts/gin_choice_provenance.py build --output <新目录>`。

## 实现与证据

- 适配层声明第四个参数是一个独立控制字节指针。二进制规划器从 `CMPB 0(DI), $0` 的内存操作数定位比较指令，不手填指令地址；核对 ELF 字节并生成 load 快照。
- 共用 ByteMachine 支持字节内存比较。对于已声明的额外控制输入，每次比较都必须有对应的运行时快照；没有证据时返回 unknown，不能把未读取的字节默认为零。
- selective 在两次保留的比较事件之间重放静态指令，并检查比较位置、寄存器、内存地址、事件数量及出口状态。动态分支控制复制源，具体字节来源仍由被执行的赋值指令推导。
- 输出来源图仍表示显式数据依赖。control 用于确定分支，不作为被复制到输出中的数据源；本轮不建立完整隐式流图。
- 每请求缺失控制证据、缺少/重复比较事件、快照地址错误，以及既有 HTTP/SDK 负向检查都单独验收。自然线程迁移如实统计，并发重叠仍是运行门槛。

归档保留 `full/choice`、`boundary/choice`、`selective/choice`、`entry/choice` 的事件、计划、来源图、SDK span 与评价；共同二进制只保存在 `build/<role>/gin-byte-target`。boundary 的 `evaluation.json` 列出八个请求各自的 unknown 原因；顶层 `comparison.json` 比较 full/selective/entry 的逐字节来源和两种补采策略的输入事件数。

## 什么时候可以只读一次

entry 模式使用一个保守的充分条件检查器 `observation_contract.stable_runtime_input`。它检查整个已解码叶函数，而不只检查本次走过的分支：

1. 只包含支持范围内的指令，没有调用或未建模副作用；控制输入通过不变的 DI 地址读取。
2. 写内存指令只通过不变的 AX 输出地址执行，禁止向控制地址写入或通过其他未知基址写入。重建时进一步逐次检查写入确实落在四字节输出范围，并检查 control 与所有数据区域不重叠。
3. 控制字节在函数第一条指令前采样，CFG 不允许跳回入口，从而保证每请求一次；入口事件缺失、重复或地址不符都拒绝解析。
4. 场景明确声明控制对象由请求私有持有，没有外部写入。**这是环境与对象所有权前提，不是该二进制检查器自动推导出的事实。**缺少这项声明不生成 entry 计划。

检查结果保存为 `plan.json` 的 `entry_stability`，并在重建时重新核对，避免盲目信任旧结果。循环内比较依然逐次重放；它们使用同一份入口值，并在 `instruction_steps` 中标记 `reused-entry-snapshot` 和实际入口事件编号。没有把四次比较伪装成四次实际采样。

测试会注入控制地址写入、未知别名写入、基址寄存器改写、未建模调用、跳回入口、缺失私有持有声明等情况，检查器必须拒绝 entry 优化。这里的拒绝表示当前充分条件无法证明可复用，**不等于数学上证明了每次都必须采样**；更强的别名分析或对内部写入的建模，可能允许进一步优化。

## 不能从本实验推出的结论

这里的“边界不足”针对**固定的原有快照内容**，不是说任何边界观测方案都无能为力。entry 正是在原有观测之外补充一次入口读取。本轮比较两个明确的候选策略，并给入口值复用设置充分条件，不声称已经找到全局最优位置或最少事件数。

选点依赖已声明的一字节参数、支持范围内的指令与简单直接寻址，还没有实现通用未知输入发现、别名分析或自动优化器。`readControl` 的调用边界被显式允许；该 helper 内部来源不在本次追踪范围。不能以此宣称支持任意未配置函数。

控制对象和数据缓冲区由请求私有持有。本轮不覆盖别的线程在 uprobe 读取快照与真实比较之间修改 control 的竞争，也不覆盖未建模的共享内存写入、间接调用或任意字段。

## 本地验证

独立编写的两份完整指令轨迹分别走上游/本地分支，边界数据与寄存器一致（不将时间戳作为来源证据），实际来源不同。full/selective 均给出正确来源，boundary 均拒绝归因；交错请求及破坏采集证据的检查通过。

真实 Go/Gin 服务与客户端已构建，三种探针计划生成通过。原生 HTTP 测试另外把本地 B 改为 `LOCL`，确认请求确实进入两条业务分支，并核对八条 SDK 调用链；正式 BPF 场景仍使用相同值 `SAME`。此前主机归档的 192 次 full 本地计算回归不变，并可在没有额外控制输入时重放为零内部事件的 selective 模式。

新增 entry 的本地测试覆盖两种控制取值与相同值不同来源、四次比较引用同一入口事件、破坏入口事件后的拒绝，以及上述稳定性检查失败情况。新的真实 Gin 构建、四种计划生成和原生 HTTP/SDK 检查通过；此前三种模式的主机归档可按新核心重新解析，结果不变。

本地无法加载 BCC；新增 entry 的真实采集与重建仍需主机归档验证。本实验不报告性能结论。
