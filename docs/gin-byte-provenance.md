# Gin 与当前来源核心的集成回归

## 状态与目的

此前 Gin 默认调度验证已经覆盖 28 个请求、892 条真实 eBPF 事件，观察到请求重叠，但自然线程迁移次数为 0。另一份受控迁移归档覆盖 28 个迁移请求、892 条事件。这两份归档已在本次集成时重新推断，结果与历史记录完全一致。不能将受控迁移与默认调度实验的结论混为一谈。

当前赋值套件的六个独立用例也已通过真实主机采集核验：358 条事件，赋值保留 A/C、部分覆盖保留 A/C 和 B、完整覆盖只保留 B。该套件到此冻结为回归基线。

本轮只做集成：把这三种已经验证的业务函数放回 Gin，并接入 `byte_provenance.py`。不增加加工类型或跨服务功能。**本地构建、24 次真实 HTTP 响应、30 项相关测试已通过；新集成场景的真实 eBPF 采集尚未验证。**

## 复现

继续使用 Linux amd64、Go 1.25.4、Gin 1.11.0、系统 Python 与 BCC。复用此前 Gin 的 go.mod/go.sum，无需 Docker。

```bash
cd ~/tracefusion2
git pull --ff-only
sudo env "PATH=$PATH" GOPROXY=https://goproxy.cn,direct \
  /usr/bin/python3 scripts/gin_byte_provenance.py run
```

成功或失败都会输出 `Return this archive: ...zip`。请返回整个 ZIP。只有编译可使用 `build --output <新目录>`。默认环境中不要设置 GOMAXPROCS 或调度相关 GODEBUG 覆盖项。

脚本构建三个目标，每个服务执行 8 个请求，客户端 4 个工作线程各自通过持久连接发送两次请求。服务端不固定线程，不设置 GOMAXPROCS，不主动 yield，不设阶段屏障或人为延时。来源读取和输出对象为请求私有。

## 复用与适配

- 复用原 Gin 默认场景的路由 `/account/summary`、`c.JSON`、服务启动/关闭方式及默认调度元数据检查。新场景主程序仅将业务输入换成三次四字节文件读取，业务函数直接取自冻结的赋值套件。
- 复用原 Gin 框架边界列表、`scope_plan` 的栈检查快速分支入口及 RET 探针规划。使用普通指令 uprobe，不改写 Go 返回地址，也不用 uretprobe。
- 复用 `gin_migration_boundaries.groups` 的进程/G/请求代次检查，原始 TID 保留。新事件格式先按实际作用域入口/退出建立代次，再交给旧分组检查；它不是原采集器的二进制兼容替换。
- 复用当前全寄存器采集布局、BCC 采集生命周期和 `ByteMachine`。增加的 Gin 过滤器仅按目标进程内的 R14/G 维护活动作用域，不用 TID 存储来源状态。
- `string_capture.collect` 新增可选 HTTP 客户端驱动，主线程同时持续消费 perf 事件；原调用不提供驱动时保持原流程。
- 来源推断器不读取客户端 ticket、source 查询参数、响应文件或期望来源。请求来源图中的 ID 加上作用域代次前缀，防止同值数据、复用 G 或地址导致图节点混合。

## 真实 JSON 边界

普通结构体为 `struct { Result [4]byte json:"result" }`，实际响应是：

```json
{"result":[83,65,77,69]}
```

四个数字是 `SAME` 的字节。采用数组让已验证的四字节输出缓冲区直接成为结构体字段，避免本轮另加字符串复制模型；仍调用 Gin 自己的 `c.JSON`，没有预先编码后直接发送 JSON。

观察并检查顺序：`render.WriteJSON` 入口 → `encoding/json.Marshal` 入口/返回 → `responseWriter.Write` 入口/返回 → render 返回。要求序列化对象地址、类型和内容一致，Marshal 返回切片与 Writer 入参为同一切片，写入长度完整且错误为空。随后调用原来源核心重放业务指令。JSON 采用明确的 `gin-byte-array-v1` 摘要，不分析反射和编码库的全部内部指令。

输出结果终点是 Gin Writer 接受的正文；客户端实际收到的状态、类型与正文仅作为独立评估。没有把“Writer 接受”直接声称为网络对端已收到。

## 正确性与通过条件

每种业务均交替选择 A/C，三份文件内容完全相同。不同请求使用不同目录下的文件，评估时将实际观测的三次读取路径与客户端请求一一核对。

| 目标 | 选 A 的最终来源 | 选 C 的最终来源 |
| --- | --- | --- |
| assign | A | C |
| partial | A、B | B、C |
| overwrite | B，清除 A | B，清除 C |

同时要求来源变化历史、旧来源移除、24 个响应正文正确；采集无报告丢失、读取或提交错误。自然并发覆盖单独检查：每个目标至少观察到两个请求作用域重叠。若来源正确但没有重叠，报告覆盖不足，不声称并发验证通过。

自然线程迁移不强制要求发生，报告 `migrated_requests` 的实际值。合成事件测试覆盖线程切换，但不替代新场景真实迁移证据。也不以作用域重叠或多线程证明同时占用多个 CPU。

每个请求预期事件：assign 49、partial 67、overwrite 81；24 请求共 1576 条。必须检查完整事件内容而非仅检查计数。全局框架探针还可能命中作用域外的启动/调度元数据编码，过滤器不提交这些事件，因此 `probe_hits` 可以大于 `submitted`。

六类离线负向检查包括丢失作用域、错误 G、错误 Writer、正文变化、缺失存储和显式采集丢失。只验证当前契约下的异常，不承诺发现任意未观测写入。

## 本地验证与边界

- 三个目标真实构建，规划 ELF 地址并逐项核对指令字节；复用固定框架版本并记录源码/框架哈希。
- 三个服务真实启动，24 次 HTTP 请求全部返回正确正文。
- 30 项相关测试通过：此前 25 项加 5 项 Gin 集成测试。包含交错请求、同 G/地址顺序复用、合成 TID 切换、来源图隔离、框架对象/Writer 身份、部分写入失败及覆盖率门槛。
- 重放历史默认调度与受控迁移归档，共 1784 条真实事件，结果保持一致。

当前限制：固定 Go/Gin 版本、关闭内联、独立四字节输入、单请求内一条观测 G、受限业务叶函数、已配置读取和 JSON 边界。新构建使用 ET_EXEC 以复用当前采集器的地址挂接；原 Gin 基线的 PIE 构建不变。读取来源是 `readValue` 的一次调用及返回，不是数据库行或内核读取偏移。暂不覆盖跨 G 数据传递、共享可变对象、任意 JSON/自定义 Marshaler、栈搬迁中的对象身份迁移或跨服务传播。尚未测量运行开销。

验收完成后进入跨服务来源衔接，不继续添加基础加工用例。
