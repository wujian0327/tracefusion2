# Go → Go 跨服务来源衔接

## 状态

这是已完成 Gin 单服务验收后的下一阶段，不新增基础加工类型。单服务归档 `gin-byte-provenance-20261004-133248-427062.zip` 已验证 24 请求、1576 条真实事件、32 条正确来源关系；各组峰值 3 个请求作用域重叠，4 个 G 各处理两次请求，未观察到请求内自然线程迁移。本次代码修改后已重放该归档，推断结果不变。

本轮真实双进程 HTTP 流程已在本地跑通：三组各 8 次外部请求，合计 24 次下游请求和 24 次上游调用。六个目标已构建并从实际二进制生成完整探针与采集器。38 项相关测试通过（包括来源推断、图拼接的合成事件测试和实际二进制计划检查），**新的双服务 eBPF 采集仍需主机运行验证**。本地 HTTP 正文正确不等于动态来源已在主机验证。

## 运行

沿用 Go 1.25.4、Gin 1.11.0、Linux amd64、系统 Python 和 BCC，不需要 Docker。

```bash
cd ~/tracefusion2
git pull --ff-only
sudo env "PATH=$PATH" GOPROXY=https://goproxy.cn,direct \
  /usr/bin/python3 scripts/gin_cross_provenance.py run
```

会依次运行 assign、partial、overwrite 三组。每组先构建两个服务，再分别启动两个采集进程；上游就绪后，下游才开始。成功或失败均生成 ZIP 并打印路径。请返回整个归档。单服务旧命令不需要再跑。

`build --output <新目录>` 只构建和生成采集器预览。实际 collect 仍需要 BCC。预览不代表内核编译、挂接成功。

## 业务路径与真值

外部客户端请求下游聚合服务，下游同步请求上游数据服务；数据流则从上游返回下游。

- 上游独立读取 A、B、C，内容全部为 `SAME`，根据请求选择 A 或 C，使用冻结的 assign 函数产生 JSON 字段。
- 下游将 HTTP JSON 的 `$.result` 解码到自己的四字节数组，再独立读取本地 B、C。
- 下游使用冻结的 assign、partial 或 overwrite 函数，然后由真实 `c.JSON` 返回。
- 每个请求的读取文件位于独立目录。所有输出仍相同，因此不能靠值相等判断来源。

| 下游操作 | 应追到的最终来源 |
| --- | --- |
| assign | 本次上游选择的 A 或 C |
| partial | 本次上游选择的 A/C，加下游本地 B |
| overwrite | 仅下游本地 B，上游不再贡献最终输出 |

客户端的 ticket、source 选择和 trace 记录只进入评估；推断器只读采集事件与配置。评估将最终源文件路径及服务身份与独立场景真值比较，而不是把 trace 匹配成功视为溯源成功。

## Trace 只解决调用候选

沿用仓库 Sock Shop 客户端使用的 W3C `traceparent` 格式，本轮客户端同组共享一个 trace ID，每次请求使用不同的 parent ID。服务代码用普通 `c.GetHeader` 读取上下文，下游通过普通 `http.Header.Set` 原样转发。没有注入来源编号、字段标签或专供探针使用的通知函数。

此版本是**最小 trace 上下文转发夹具，不是完整 OpenTelemetry SDK/Collector 接入**，没有导出完整 server/client span 树，也不把“两个服务使用相同 trace ID”当作足够证据。单个上下文限定为一次同步远程请求，无重试、缓存命中或扇出。新增业务函数用于这个可控实验；尚未证明任意存量服务都能直接套用当前 ABI 配置。

传输上下文参考 [W3C Trace Context](https://www.w3.org/TR/trace-context/)。本轮只接受版本 00、非零 trace/parent ID、采样标志 01。输入 trace 假定可信；不声称能防御伪造上下文。

## 观测证据

每端继续使用既有 Gin 请求作用域、进程/G/代次隔离、业务指令回放和 JSON Writer 检查。新增的观测位置由对应二进制的调用点及返回继续位置规划：

1. 两端 `c.GetHeader` 返回值：实际收到的 trace 上下文。
2. 下游 `readRemote` 调用参数，以及 `http.Header.Set` 参数：远程地址与实际设置的 traceparent 一致。
3. 上游 Gin 的 Marshal/Writer 边界：实际生成并被 Writer 接受的 JSON。
4. 下游 `io.ReadAll` 返回，以及 `json.Unmarshal` 调用/返回：实际收到的正文、交给解码器的同一缓冲区、错误状态。
5. 下游解码目标地址与 `readRemote` 返回对象地址：确认接入来源核心的是这一份解码数据。

当前 `readRemote` 与 JSON 数组解析采用明确的边界摘要，不完整跟踪 HTTP/JSON 库的所有内部指令。固定场景源码检查 HTTP 200 并拒绝读取/解码错误；不推广为任意响应中间件、重定向、重试或字段转换的精确模型。

## 图拼接算法

先独立重建两个服务的请求内来源图，再按实际观测的 `(trace-id, parent-id)` 查找候选。必须恰好存在一个上游响应与一个下游远程读取；缺失、重复或歧义均输出 unknown。仅内容相同不能创建跨服务边。

接着验证上游 Writer 正文与下游收到的正文一致，且接收缓冲区确实交给解码器，解码出的数组与返回给业务函数的对象一致。在固定数组模型下，把上游 `$.result[i]` 的依赖连接到下游远程读取的第 i 个位置，边类型为 `http-json-field`。替换临时的远程读取根定义后，从下游最终 Writer 反向切片，汇总终端源文件。

内部位置映射用于避免覆盖造成误归因；用户结果仍是最终来源集合和来源图。合成测试额外检查：如果上游自身也合并过来源，下游又覆盖部分位置，不应简单合并上游全部来源而留下已被覆盖的贡献。

图节点带服务与请求代次前缀。完整覆盖远程数据时，最终切片不保留上游来源节点，但调用/传输证据仍记录该调用确实发生过。

## 结果与验收

每组目录包含：

- `upstream/capture/events.json`、`downstream/capture/events.json`：两端独立原始事件及采集统计。
- 两端的 `inference.json`：各自来源图与传输边界证据。
- `joined.json`：跨服务来源图、最终源路径、传输是否仍贡献输出。
- `evaluation.json`：来源真值、客户端正文、默认调度与自然并发覆盖、负向检查。

正确性和覆盖率分开报告。两端各应观察到请求作用域重叠；如果没有重叠，报告覆盖不足，不假装完成并发验收。自然迁移发生次数如实报告，不强制发生。本轮不评估性能。

预期每个上游请求 51 条事件；下游 assign/partial/overwrite 分别 57/75/89 条。三组共 2992 条事件（24 个上游请求、24 个下游请求）。事件数量只作诊断，仍需检查地址、正文、请求身份和依赖关系。

五类离线拼接负向检查：缺少上游、上下文歧义、相同正文但 span 不匹配、收发正文不同、缺少传输证据。单元测试另行破坏原始 Header/ReadAll/Unmarshal 事件，要求拒绝拼接。这些受控检查不等于可以检测任意未配置传播路径。

## 当前边界

同机两个 Go/Gin 进程、一个同步 HTTP 调用、固定四字节数组 JSON、已知文件读取/接收边界、关闭内联。使用既有 trace 格式，但只做受信任上下文转发；没有通用异构协议识别、跨 G 数据传递、任意结构体布局、数据库行级来源或无配置接入能力。下一阶段是否扩语言或真实应用，取决于本轮证据，不在这次一起扩展。
