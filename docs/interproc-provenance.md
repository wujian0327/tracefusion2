# 跨函数动态来源重建验证

这是已通过主机验证的 [单函数闭环](hybrid-provenance.md) 的下一阶段。新增直接调用、参数与返回值传播、栈保存/恢复及调用上下文；**本版真实 BCC/eBPF 运行尚待主机验证**。本地指令模拟通过不等于新 BPF 程序已经加载成功。

## 运行

沿用已跑通的 Linux x86-64 / WSL2、系统 Python BCC、GCC 与 binutils 环境。无需 Docker 或额外运行时依赖。

```bash
git pull origin main
sudo /usr/bin/python3 scripts/interproc_provenance.py run
```

成功或失败均返回 `artifacts/interproc-provenance-*.zip`。只查看静态结果可运行：

```bash
python3 scripts/interproc_provenance.py build
```

配置仍只包含入口函数、输入/输出结构体布局和目标字段。辅助函数及调用位置由二进制直接调用目标自动发现，不需手写每个函数的传播摘要。

## 验证三个问题

| 入口 | 数据经过的过程 | 核心检查 |
| --- | --- | --- |
| `pipeline_branch` | 选择来源 → 嵌套读取 → 返回 → 栈上暂存/重载 → XOR → 写入输出 | 参数、返回值和栈局部变量的来源能否接起来 |
| `pipeline_repeat` | 同一读取函数先取敏感字段并写入，再取普通字段覆盖 | 同一辅助函数的两次调用是否混淆；最终图是否排除第一次来源 |
| `pipeline_merge` | 选择一个来源，再独立读取普通字段 → 合并计算 → 写入 | 多个返回值合并时是否保留正确来源集合 |

两组数据、每个入口两种选择，共 12 次入口调用。敏感与普通字段故意取相同数值；推断不能依靠数值相等区分来源。业务操作没有追踪 API 或标签；`volatile` 用于保留实验中的栈暂存与输出写入。

当前 GCC 构建从三个入口自动发现六个辅助函数：两个字段读取函数、选择函数、编码函数、合并函数和写入函数。函数名称不参与来源推断。

## 算法与实现

### 静态规划

1. 从入口沿直接 `call` 发现函数，建立跨函数控制流。拒绝递归、循环、外部/PLT 调用、间接调用和尾调用；不能用“忽略该调用”继续给出确定结果。
2. 有界枚举跨函数候选路径。每个指令定义带有入口和调用点序列作为上下文，两个调用点调用同一个辅助函数仍有不同的定义身份。最多八层调用、每函数 128 条指令、每条展开路径 512 步、每入口 128 条枚举路径。
3. 解释寄存器、输入/输出字段以及有界栈内存的定义—使用关系。参数通过真实 ABI 寄存器传递；返回值按实际 RAX 操作传播；调用压入返回地址，返回校验并恢复栈位置。
4. 对明确的常量条件排除不可能路径。例如 `pipeline_repeat` 的两次选择参数是 1 和 0，这一事实来自机器指令，而不是测试真值。对运行输入决定的分支仍保留候选。
5. 从目标字段反向取依赖，同时保留函数边界、调用前后、分支和必要栈操作，生成物理探针位置的并集。

指令可能产生多个定义。本版将返回值定义与栈指针定义分开：不能因为一条 `ret` 同时涉及返回值和栈恢复，就把旧返回值来源错误地传给后续栈地址。重复调用后的覆盖测试检查了这一点。

### 动态采集与重放

采集器为每个线程维护外层调用编号及函数栈。事件记录当前函数、调用深度、外层输入/输出地址、寄存器、标志位，以及入口栈顶以下 256 字节和入口返回地址。基址在入口保存，不能从参数寄存器已改变的辅助函数里重新猜测。

事件结构超过 BPF 512 字节栈预算，使用 per-CPU map 作为事件暂存区。所有探针仍限定本次子进程 PID；采集计数、丢失及读取错误沿用已有检查。

推断使用原始事件匹配跨函数候选路径，逐点检查：

- 运行 IP 与 ELF/进程映射是否一致；事件顺序、函数及深度是否匹配。
- 参数寄存器、返回值、字段内存、已写入的栈位置与解码指令是否相容。
- 每次内部返回是否回到匹配调用点；入口结束时栈位置和 callee-saved 寄存器是否恢复。
- 栈、输入、输出内存是否超出声明范围或相互重叠。

输出包含每次入口调用的 `call_instances` 和带上下文的 `dependency_graph`，其中参数和返回传递有独立的边类型。未观测到的指令依赖明确的静态语义模型；不会把整张静态并集图直接标成全部真实发生的依赖。

## 本地验证（2026-10-01）

开发环境没有 BCC。使用 Unicorn 2.1.4 独立执行实际编译的 ELF 字节产生**模拟观测**，另将 C 程序原生执行的输出作为独立评估输入。推断接口不读取 stdout/预期来源。

- 完整测试 66 项通过，包含原有 60 项和新增 6 项；已安装可选 Unicorn，没有跳过模拟执行测试。
- 当前 GCC 13.3.0 构建：9 个函数、82 条范围内指令、81 个观测位置，12 次入口调用、72 次函数进入、最大深度 3、448 条模拟事件。
- 仅静态来源关系 TP=14、FP=6、FN=0；结合模拟观测后 TP=14、FP=0、FN=0。该指标只用于本夹具，不能作为真实主机结果或完整图边召回率。
- 函数入口和辅助函数全部改名、代码地址变化、变换常量改变后，自动发现和重建仍通过；没有增加对应函数名的推断规则。
- 栈返回地址、调用深度、寄存器、根调用身份、读取状态或 IP 被篡改，以及事件缺失/重复，均拒绝通过。丢失整次入口调用也不能通过评估。

本轮仅少量减少范围内的探针，**没有证明低开销，也不声称完成最小观测点选择**。先验证调用状态和传播语义，后续再根据测量精简。

开发测试依赖仍见 `tests/hybrid-requirements.txt`；主机采集不需要 Unicorn。

## 结果包与验收

### 首次主机加载失败与修正（2026-10-01）

用户回传 `interproc-provenance-20261001-172026-33ca.zip`：原生程序构建成功，BCC 0.29.1 在加载 `probe_0_4` 时失败，收到 0 条事件。验证器在 `s->frames[d-1]` 报告 `R2 unbounded memory access`。`Permission denied` 是这次 BPF 加载拒绝的外层异常，不能据此要求调整 sudo 权限。

日志显示深度检查经编译器范围折叠后，验证器未将范围约束传回用于数组寻址的寄存器。修正同时覆盖帧读取和写入：保留非法深度拒绝，在寻址前加入带编译器屏障的显式下标掩码，并要求栈容量为二的幂。掩码不用于容忍非法调用状态。

修正后本地 66 项测试仍通过；开发环境不能加载 BPF，修正后的真实主机采集仍待重跑。本次失败没有产生可用于来源准确率评估的数据。

文件结构沿用单函数实验，包括配置/源码、实际 ELF、反汇编、自动生成的计划、BPF 源码、进程映射、挂接记录、原始事件、计数、推断图及独立评估。

- `probe-plan.json`：所有自动发现的函数，入口的上下文路径及依赖边，物理探针位置。
- `events.jsonl`：新增 `root`、`depth`、`root_sp`、`stack`、`stack_error`；`call_id` 指外层入口调用。
- `inferred.json`：外层调用对应的来源、函数实例列表和依赖子图。
- `result.json`：`build_verified` 仅表示静态构建成功；`ebpf_checks_passed` 需要真实采集、状态检查和独立评估全部通过。

主机编译器可能产生不同指令数量，验收不写死 81/448。保留失败包才能区分指令模型不足、BPF 编译/验证失败和事件不完整。

## 边界

支持单线程、无环、无递归的已解析直接调用，入口 ABI 固定为 `(output*, input*, int)`；字段布局仍是显式连续 uint32。栈访问必须位于规定窗口，拒绝未建模的读取或部分重叠访问。只报告显式数据依赖，不报告隐式控制污点。

尚不支持任意库函数、动态分配、字符串、函数指针、JIT、并发和跨服务。调用点上下文仅在此无环范围内区分调用实例，不能推广成循环/递归中的完整历史版本。
