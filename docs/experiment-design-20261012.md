## 1. 核心主张与范围

拟检验的论文主张：

> 对用户指定的来源边界和目标字段，结合机器码或字节码静态分析与选择性运行观测，
> 恢复实际执行中的字段来源，并以较低的完整分析成本适配多种语言的服务程序。

这是待验证的研究主张，不是任意程序的能力保证。主要定位是软件工程中的程序理解和数据传播诊断；
准确率、低成本、多语言复用分别以对应证据支持。跨服务字段连接通过原始应用验证之前，
不把标题扩大为通用跨语言微服务端到端溯源。已有受控 Gin/OTel 证据保留，但不替代此项。

固定语义为声明模型中的直接数据来源；地址依赖、控制影响、对象身份分别记录。
人工配置的来源边界、ABI/布局、运行时摘要和不可变性契约全部披露。
Java 使用字节码前端，不能称为 eBPF 已经直接完成 Java 字段分析。
当前 Java 方法闭包绑定与可恢复步骤省略，不等于已实现字段目标驱动的最优选点。
C、Go、Java 的既有局部证据不自动证明 Rust/C++、一般并发或完整框架支持。

## 2. 只回答四个研究问题

| 问题 | 主要证据 |
| --- | --- |
| RQ1：来源答案是否准确、完整？ | 独立真值、外部标签、逐查询集合比较、unknown/失败统计 |
| RQ2：相对外部工具的在线与完整成本如何？ | 同一开源对象、负载、来源/目标下的资源和耗时 |
| RQ3：方法能复用到哪些语言和执行环境？ | 已验证路径、公共规则、前端差异、支持与失败矩阵 |
| RQ4：选择性观测对收益有什么贡献？ | 少量 full/sparse 消融；已有 boundary 强对照保留 |

跨服务实验同时为 RQ1/RQ3 提供证据，单列消息连接成本。
不要求每个对象都赢；不要求所有语言与所有外部工具做全组合。

## 3. 对照系统与比较资格

主实验为 **native / TraceFusion / 外部工具** 三组。我们的方法配置在正式测量前冻结，
不能每个测试输入测完后挑最快模式冒充自动策略；如报告 sparse 和 boundary，两者分别命名。

| 对照 | 第一轮角色 | 接入及结论边界 |
| --- | --- | --- |
| Galette | Java 主要外部对照 | 沿用固定上游版本与实际标签接口；现有原版 Commons Codec 路径已跑通 |
| libdft64 | C/C++ 主要外部对照 | 沿用固定版本；必须先检查目标指令和标签传播是否覆盖 |
| HardTaint | 相关工作、延期候选 | 按此前决定不启动硬件部署或自称复现 |
| FlowDist | 跨服务后续候选 | 先核对语言、语义与运行条件，不作为首批完成门槛 |

Galette 与 libdft64 比较衡量实际系统成本，不统一称为“其他剪枝算法”。
需要增加对照时，优先补覆盖缺口或最近方法，不能只为凑数量增加同类工具。
不支持、启动失败、语义不匹配是不同状态；均不算我们正确性或性能获胜。

共同语义检查必须包括字段/字节粒度、移位/掩码、数组索引、控制影响和运行时摘要。
可对齐部分报告同语义结果；无法对齐部分保留原始答案及差异解释，另表呈现。
不得删除外部工具的额外标签来制造一致性。若采用来源投影，事先固定映射并保留投影前后结果。

### 4.1 已有证据直接复用

| 对象 | 现有证据 | 本轮缺口 |

证据入口：
- [Go 四方法结果](../experiments/checkout-payment-path/METHOD-RESULTS.md)

- ngiflib 的额外字节关联涉及语义/指令支持差异，不能作为同语义强基线准确率结论。

### 4.2 新对象先过可行性检查

| 优先级 | 开源候选 | 拟检查的原始路径 | 外部对照 | 当前状态 |
| --- | --- | --- | --- | --- |
| P0 | 固定 Online Boutique 版本的 Java adservice | 原始 RPC 响应字段生成、读取和传递 | Galette | 候选，双方完整服务兼容性未验证 |
| P1 | DeathStarBench Social Network 的 C++ 服务 | 原始结构化字段或文本处理路径 | libdft64 | 候选，具体服务/版本/目标待冻结 |
| P2 | ripgrep，Rust | 匹配输出内容与输入文件字节的关系 | libdft64 兼容性候选 | 候选，不能保证原始 Rust 二进制可支持 |

首先沿用现有 Online Boutique 版本核查 Java 服务，避免默认换到最新版本。
Java adservice 的类别词可能仅控制广告选择；来源内容可能实际是配置/常量。
必须独立定义直接数据来源，不能把控制选择混成数据传播。
当前 Java 引擎的静态方法、类型、线程等限制可能直接阻止原始 RPC 路径；
如果需要扩展，先列出具体缺口与工作量，不能替换原逻辑后仍称完整服务支持。

不把自写 HTTP 包装库当作新增原始服务；批处理驱动可以调用未修改的上游函数，
但须标为驱动实验。只分析原函数片段则报告路径实验，不报告整个服务覆盖。
候选选择依据真实使用、查询意义、独立真值和可审计适配，不依据预期胜率。
已尝试但不兼容的候选及原因也进入最终适用性表。

每个候选进入正式测量前，生成一页接入记录：
1. 上游 URL、提交、依赖、构建选项、二进制/class 摘要和业务改动清单。
2. 一个具体来源—目标查询、请求实例身份与独立真值办法。
3. 原生功能验证；我们和外部工具的状态、日志及语义校准。
4. 采集范围、来源快照、运行时契约、缺失支持。
5. 结论：正式接入 / 仅路径验证 / 因明确问题暂缓。失败不得删除。

## 5. 查询与独立真值

首批每个可接入对象选择 2–3 个有不同意义的查询（不是硬性凑数），在测量前冻结。
优先使用上游测试和正常业务输入，再补同值不同源、覆盖、重复记录/请求等区分性输入。
输入规模覆盖小、中、大三档，具体数值依据原程序和支持上限在预实验后登记。
不超过 Go 已声明商品/数量上限，也不把现有小数组界限当作大型服务覆盖。

一个查询的完整定义至少记录：
`query_id, upstream_revision, source_boundary, source_identity, sink_location,
target_field, dependency_semantics, scope, contracts, oracle, expected_status`。

来源身份保留调用/请求、对象或读取实例及字段/元素位置，不以值相等建立边。
独立真值可由格式规范、人工审定数据流、独立参考模型或验证专用标记获得；
外部工具和 full 模式均不能单独充当真值。真值程序不得被我们的规划器/推断器读取。
源码标记只用于独立验证，不能计入正式业务计时或泄露答案给被测系统。

主表报告：
- 集合完全正确数 / 全部有目标的有效查询数；unknown/采集失败仍在该分母中。
- 成功回答数、错误数、unknown 数及原因；来源边级 TP/FP/FN、Precision/Recall。
- 空来源集合的准确性独立处理，边级分母为零报告 N/A，不填 100%。
- no_sink 和业务错误单列，按实际执行核对，不当成正确字段答案。
- 查询类型数、独立输入数、动态查询次数分别统计；重复运行不增加覆盖。
- 跨请求/重试错误关联数量。

明确不支持的输入另外组成拒绝检查，不混入共同支持任务的性能胜负比较。

## 6. 正式性能协议

### 6.1 预实验与冻结

预实验仅用于确定支持范围、负载及测量窗口，不进入正式统计。
每个对象先登记同一硬件、操作系统/虚拟化、编译器/JDK、CPU 分配、内存限制、
GC/JIT 配置、存储位置、客户端位置、背景服务和工具版本。

建议首轮正式协议为 **10 个独立配对区组**，每个区组运行 native/ours/external，
顺序按固定种子随机化并保存。各组新进程独立预热；
区组是统计重复单位，进程中的大量请求不当作独立重复。
资源不足需调整时，在正式测量前统一登记，不根据胜负或显著性追加/停止样本。

### 6.2 服务与批处理分开

服务：
- 用 native 预实验确定参考处理能力（固定延迟阈值与错误率要求），保存该定义。
- 低/中/高负载初始取参考能力的 20%/50%/80%，所有方法接收相同绝对请求率。
- 使用独立压测端的开放式到达计划，保存计划与实际发出时间；工具过载时不悄悄降压。
- 记录排队、超时、错误和实际成功吞吐；避免仅统计快速成功请求掩盖过载。
- 正式窗口初始设 120 秒；预实验若需要更长则统一冻结。
  请求数不足以稳定估计 p99 时延长预注册窗口或不报告该分位数。
- 可另做相同 SLO 下容量比较，但不与固定负载结果混算。

批处理：
- 分别报告新进程完整命令与同进程批量处理。
- 不通过不断启动新 JVM/Pin 冒充稳态；原软件不支持持久处理时明确记录。
- 自定义批处理驱动只调用原始上游路径，单独标注；不能宣称原 CLI 具有该服务模式。

JVM/运行时预热：
- 每个实际被测进程内预热；另起 JVM 的“准备轮”不能预热正式进程的 JIT。
- 预实验确定统一预热时长，保存 GC/JIT 与分窗延迟/吞吐趋势。
- 若稳定性证据不足，报告“预热后测量”，不宣称达到稳态。
- 预热数据和正式数据边界明确；状态重置不得破坏来源身份或隐藏清理开销。
- 构建、静态规划、JDK 插桩、BPF 编译/挂载、启动分别记录，不混入稳态区间。

### 6.3 测量口径

| 类别 | 指标及计费规则 |
| --- | --- |
| 业务 | 成功吞吐、错误/超时率、p50/p95/p99、业务进程 CPU |
| 采集 | 独立采集器 CPU/RSS、事件数、实际字节、丢失和读取错误 |
| 还原 | CPU、墙钟、峰值内存、完成查询数、失败数、队列/未完成工作 |
| 完整 | 所有分析相关进程累计 CPU、查询完成时间、在线/离线资源分项 |

Agent/Pin 的工作在业务进程内，报告合计 CPU，不伪造纯业务/纯采集分离。
以 cgroup 或明确的 PID/子进程清单覆盖被测进程；压测端成本单列。
先验证资源计量不会继承父 Python 堆或漏算子进程，再报告内存优势。
各进程峰值相加不是同时总峰值；进程 RSS 和 cgroup memory.peak 的口径不同，分别说明。

在线与离线顺序执行的批任务，可逐次相加时间；流水执行服务不能相加阶段墙钟，
应直接测量目标事件到来源答案完成的延迟，并报告处理积压。
当前只有批量离线工具时，保存整个测量窗口并测量全部还原及排空成本；
该结果不能被称为实时分析。跨主机计时需校准或使用可靠的统一时间基准。

外部工具标签传播、标签提取及我们来源重建/查询都计入成本。
若需要统一结果序列化，保存相同答案格式；诊断大图导出单列，不能只让一方承担。
缓冲写入与 fsync 持久化成本区分，保存输出大小和实际配置。
丢失、崩溃、超时、unknown 不能从结果集静默删除；不完整分析的低成本不算优势。
正式成本仍核对每个查询，验证器在计时外运行。吞吐过载记录保留，不伪装成功运行。

报告每个区组原始值与配对比例 `1 - ours/external`，给出中位数及区组级 bootstrap
95% 置信区间（固定种子和重采样数）。接近零的基线同时报告绝对差值。
应用分别展示，不把数千个动态查询当成数千个独立应用，也不混合不同协议取平均。

## 7. 消融从简，保留强对照

只在一条 Go、一条 Java 代表性路径上开展，不遍历整个对象矩阵。
第一轮做能实际实现的 full/sparse 对照，使用相同来源契约、快照和负载。
独立的静态范围裁剪开关若不存在，不为了凑“三组”把不同解释器比较称为纯消融；
后续需要时再增加，并明确改动因素。

已有 boundary 作为强方法控制组保留，特别是它已经更省成本的路径。
不自动删除边界快照内容制造失败；未知返回只能反映该实现/契约的限制，
不能由此证明内部探针在信息上必需。
不实现新的 A/B/C/D 全组合实验框架，也不新增成本自适应优化器作为本轮前置任务。

## 8. 多语言与跨服务验证

多语言表逐项记录：实际版本、支持的查询/操作、公共代码或规则、前端专用代码、
运行时摘要、接入工作和失败限制。C++/Rust 必须有真实二进制执行证据后才写“已支持”；
不把机器码理论上语言无关当成支持证据。不直接比较不同语言的原始速度。

先检查 Online Boutique 原有 Go frontend 与 Java adservice 等调用边上的实际字段传递，
不把 Java 广告服务接入原支付路径来虚构原始链路。
只选择经源码和运行证据确认的请求/响应字段连接；当前是候选，未完成端到端验证。

来源连接需同时具备消息实例身份和序列化字段映射：
发送端字段 → 实际消息字段 → 接收端字段。
trace/span ID 只能辅助请求关联，值相等或时间邻近不构成字段来源证据。
受控边界检查覆盖同值请求、并发、重试和失败，保持原始业务逻辑；
随机选择等外部状态要记录/建模，否则返回 unknown。
消息绑定适配和成本对所有可比模式一致，单列额外开销。

外部工具只能分析其中一端时，仅比较共同支持的服务内部分；
不能把两个本地污点工具输出随意拼接成“外部跨语言基线”，
也不能把外部工具不提供跨服务功能算作准确率为零。

| B：首批外部成本 | 为已有 Java 外部对比补同进程批处理；服务通过 A 后再做持续 RPC 测量 | 同输入三组、全部答案核对、完整计费、原始重复数据可复算 |
| C：Go 服务成本 | 检查现有 performance.py，接入 snapshot-v2 同口径 | 不复用旧 v1 比例；区分服务级和金额区间；保留 boundary 结果 |
| D：C++/Rust 候选 | 分别做一个原始路径的可行性审查 | 有明确通过/受限/失败证据后决定正式纳入；不预承诺四语言全支持 |
| E：整合 | 少量消融、实际跨服务连接、汇总论文图表 | 每条主张都有对应证据；负结果、契约和适配限制完整 |

阶段 A 若受当前 Java 引擎能力阻止，先完成阶段 B 已有路径的稳态缺口并列出扩展范围；
不能在没有接入评估的情况下承诺完整 Java 服务运行命令。
已有通过的独立正确性实验不默认重跑；变更到的分析代码或新路径需要定向验证。

每次正式运行归档：版本/源码摘要、二进制或 class、配置和运行命令、查询/真值、
选点计划、原始事件、外部标签、逐请求答案、阶段计时、资源原始样本、随机顺序、
退出码/丢失统计、验证报告。保存 failed 状态和失败原因。
规划器不读取真值或外部答案；验证器可以读取全部证据重新评分。

预期论文产物控制为：
1. 一张对象、语言、查询和支持范围表。
2. 一张外部工具准确性表（不等价语义另表）。
3. 两张成本图：业务影响；完整分析 CPU/答案延迟。
4. 一张小型消融图，保留 boundary 对照。
5. 一个真实业务字段来源案例，跨服务完成后展示消息连接证据。
