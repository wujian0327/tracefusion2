# 双 Gin：完整探针与边界探针对照

本轮检验一个有限命题：在当前四字节、私有缓冲区、已完整建模的确定性叶函数中，入口数据和选中对象地址足够驱动二进制指令重放；不必逐条采集循环内指令。跨服务、读取、JSON、HTTP 和请求作用域证据继续保留。

这不是通用观测点自动选择算法，也不证明任意 Go 程序只观察 if 条件就能准确溯源。

## 主机执行

依赖与[原双 Gin 实验](gin-otel-provenance.md)相同：Linux amd64、系统 Python/BCC、Go 1.25.4。不需要 Docker。执行：

```bash
cd ~/tracefusion2
git pull --ff-only
sudo env "PATH=$PATH" GOPROXY=https://goproxy.cn,direct \
  /usr/bin/python3 scripts/gin_otel_compare.py --rounds 4
```

每轮分别运行 full 和 boundary，轮间交换先后顺序。默认四轮共八次完整场景执行，每次包含 assign、partial、overwrite 三组，每组八个外部请求、四个客户端 worker。失败也会打包。请返回打印的 `artifacts/gin-otel-compare-*.zip`。

只跑边界模式：

```bash
sudo env "PATH=$PATH" GOPROXY=https://goproxy.cn,direct \
  /usr/bin/python3 scripts/gin_otel_provenance.py run --observation boundary
```

原 `gin_otel_provenance.py run` 默认仍为 full。构建命令也支持 `--observation boundary`。

## 两种模式的区别

| 部分 | full | boundary |
| --- | --- | --- |
| 读取、函数入口/出口、JSON、HTTP、请求作用域 | 保留 | 保留 |
| 业务叶函数内部 instruction 探针 | 挂载并检查每次执行状态 | 挂载前从计划删除 |
| 来源与版本重建 | 共用 ByteMachine | 共用 ByteMachine |
| 循环执行路径 | 重放并与每条指令事件核对 | 由入口快照、静态指令和模型计算 |
| 指令节点的证据 | 实际事件序号 | `modeled-from-boundaries`，事件序号为 null |
| OTel SDK span | 保留 | 保留 |

比较程序每组只构建一次服务二进制，两种模式复制同一构建产物并校验哈希。区别是探针计划；没有为 boundary 改写业务程序。采集器确实不再挂载被删除的内部探针，而不是采集后丢弃事件。

读取 A/C 的动态选择由 work 入口的实际对象地址确定。循环索引、字节复制及覆盖由二进制指令重放。来源采用对象身份和版本依赖，不凭数值相等判断。请求仍按进程/G/作用域代次隔离，跨服务仍使用 SDK 父子关系和 HTTP 字段证据拼接。

## 结果与计量范围

- `comparison.json`：事件减少比例、两种模式每轮平均请求耗时、这些均值的中位数及其比值、物理探针数量。
- `trials.json`：逐轮记录与按请求、输出字节规范化的来源，用于检查两种模式相同输入的结果一致性。
- `trials/round-*/<variant>/evaluation.json`：原有正确性、并发覆盖、负向检查，以及实际采集计数。
- `build/`：共同二进制与构建证据。为控制归档大小，trial 内重复二进制不写入 zip；`binary-index.json` 按哈希定位共同二进制。

客户端从 `http.Client.Do` 前计时，读完并关闭响应体后结束。统计包含网络、两端业务、OTel 与探针的请求期间开销，也包含首次连接；不包含编译、挂载、服务启动等待和离线分析。两种模式都启用 OTel。

这是小规模相对耗时试验，不是生产吞吐量测试。没有无探针对照，不能据此报告绝对 eBPF 开销。事件减少不保证耗时按同比例减少。每个 trial 保留原有并发作用域重叠门槛，不以降低验收标准换取通过。

## 有效边界

boundary 模式要求 `closed-four-byte-leaf-v1` 合约：输入快照完整，独立四字节缓冲区，支持范围内的叶函数指令，没有函数执行期间的外部写入、未建模调用或运行时影响。模型检查出口寄存器及交给 JSON 的字节。

缺少必需边界、选中地址无已知读取定义、出口状态矛盾等可检测错误返回 unknown。**入口/出口一致不等于证明内部没有外部干扰。**特别是未观察到的同值覆盖、隐藏别名或并发写入，可能无法凭边界证据发现；这类程序不在当前合约内，不能声称系统会自动识别所有证据不足。

本实验复用已有 SDK 接入；OTel 的初始化和中间件注册仍涉及应用配置/源码接入，不能将整个实验称为零修改。

## 已有验证与本轮待验证项

用此前主机归档对新共用核心做离线回归，三组共 24 个外部请求、48 次本地计算的跨服务来源图一致；移除内部事件后从 2992 条保留到 1008 条，减少约 66.3%。模型节点增加证据标记，不影响依赖图比较。该数字来自旧归档的证据投影，不是本轮主机性能结果。

新增回归覆盖交错请求、相同数值不同地址的选择、正反向循环、部分/完全覆盖、缺失或矛盾边界、实际探针删除，以及逐字节来源比较。实际 BCC 挂载和 full/boundary 耗时对照仍需在主机运行。

本轮本地完成六个服务二进制与计时客户端的构建、两种探针计划生成和真实 HTTP/SDK 集成。相关 Gin 测试执行 26 项通过（另外 34 项旧场景需各自构建目录，明确跳过），字节核心另 10 项通过。实际 HTTP 测试包含三组共 24 个响应的计时字段和 99 个 SDK span 检查；这不替代 BCC 验证。
