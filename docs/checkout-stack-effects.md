# 未知调用与间接写入的栈来源失效处理

日期：2026-10-08。接续 [对象依赖候选图](checkout-object-graph.md)。本轮是静态证据检查及保守失效处理，不是新的主机采集或真实请求溯源验收。

后续增加了 [实际客户端的接收者访问摘要](checkout-receiver-summary.md)。当前 CLI 为 schema 3；本页的失效规则与结果仍保持，未因条件化摘要而放宽。

## 解决的问题

上一版分析在函数调用前后保留私有栈槽的定义，并明确把“栈槽没有被别名写入”列为尚未验证的条件。如果后续直接把这种候选关系用作来源证据，遇到调用改写或间接写入就可能继续沿用旧来源。

默认分析现在移除了这个全局保留假设。遇到未建模调用，将全部受跟踪栈槽定义改为 `unknown_stack_effect`；遇到尚未证明与调用者栈隔离的间接写入，也做同样处理。未知节点包含发生位置与原因，不会自动连回调用前的来源。

这是一种有意保守的处理：**没有证明所有这些调用或写入真的修改了栈**，也没有完成精确别名分析。即使没有直接看到把 SP 地址传给调用，也不会据此保留旧来源。业务对象的堆写入若缺少足够的隔离证据，同样可能使栈关系变成未知。

## 算法与明确例外

1. 构建调用与间接写入的潜在栈副作用集合。
2. 在这些位置加入未知栈定义，重新计算 reaching-definitions 不动点。分支保留已知与未知两种候选；循环也不会消掉未知候选。后续明确的直接栈赋值可以重新建立已知定义。
3. 用新的图检查间接写入是否仍满足受信任写屏障缓冲区契约。如果缓冲区身份已被未知调用破坏，增加该写入的失效标记并重新分析，直到集合稳定。
4. 分别沿写入的值依赖和地址依赖查找未知栈节点。报告 `value_stack_blockers` 和 `address_stack_blockers`，并列出受影响的栈读取位置。

仅有固定 Go 1.25.4 运行时的显式契约可保留调用者保存槽的**逻辑来源**：`runtime.newobject`、`runtime.makeslice`、`runtime.gcWriteBarrier1..8`。这些是人工声明的运行时语义，不是本轮自动分析了全部运行时机器码。依据为固定工具链的 `runtime/malloc.go:newobject`、`runtime/slice.go:makeslice` 和 `runtime/asm_amd64.s:gcWriteBarrier`。应用业务函数、gRPC 和 fmt 调用未加入免失效白名单。

只有当间接写入的基址在新的定义图上都能追到 `gcWriteBarrierN` 返回缓冲区，且没有动态索引、写入范围完整落在 `[0, N*8)` 内时，才将其排除。超界、负偏移、丢失缓冲区身份或其它基址都保守失效。

Go 栈搬迁可以改变地址而保留逻辑来源；这些契约不表示 SP 或对象指针原始数值保持不变。仍假设正常 ABI 执行，不涵盖恶意机器码、异步 unsafe 外部写栈等。构建版本字符串本身也不是工具链或运行时未被篡改的证明。

| convertCurrency 中请求对象 `+40` 的 From 写入 | 仍可追到该函数入口 DI | 仅是本地赋值关系，不是远端币种服务的加工血缘 |

`prepOrderItems` 中有 12 个保守失效站点和 23 个受未知栈依赖影响的静态读取位置；`convertCurrency` 中分别为 5 和 1。它们是静态站点，不是动态事件数，不是最终需要的探针数，也没有证明最小性。两函数的副作用集合各在两轮分析后稳定。

这里没有将所有候选都保留为“正确”，也没有因此认定原程序存在异常改写。较多未知说明当前分析缺少调用内存摘要和对象隔离信息。**不应把上述全部读取位置都机械挂成探针，就宣称来源能够恢复。**

## 证据不足如何处理

所有受影响读取给出具体未知定义及原因。仅获得一个调用后快照，只能确认读到了什么值，不能排除同值覆盖或证明它来自哪个写入。恢复来源需要以下至少一种证据：

- 经验证的调用写范围/对象隔离摘要，能排除目标槽被改写；
- 对相关写入的运行证据，以及写入值自身的来源绑定。

无法补齐时维持 unknown。运行实例、堆版本与跨服务传输绑定仍未实现；不存在“采集器现在可以发现任何遗漏写入”的主张。
