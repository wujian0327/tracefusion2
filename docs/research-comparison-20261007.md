# TraceFusion2 与 HardTaint、FlowDist、MirrorTaint 的算法对照

核查日期：2026-10-07。当前实现固定在 `496c894e4cfd69b85af8daf284576e00a0eb009a`。本文是文献与代码对照、实验设计，不是三个外部工具的复现成绩，也没有改动溯源算法。

**结论：现有代码证明了一个限定范围的外部采集闭环，尚未证明优于现有动态分析，也没有完成自动稀疏观测算法。**下一步最有价值的是确定哪些额外观测确实不可省，并在相同来源语义下测量精度与成本。

**1. 对照口径与证据范围**

必须分别比较以下输出，不能把它们当成同一种能力：是否受污染、具体源集合、源读取实例、字段或字节位置依赖、完整历史传播路径。当前实现保留显式数据依赖；执行分支用于选择实际路径，但不将控制条件自动列为输出数据来源。因此不能拿含隐式控制流污染的报告与我们的来源集合直接计算误报率。

- HardTaint：核查 OOPSLA 2024 官方页面、arXiv v1 算法全文和 Zenodo artifact 元数据。未部署其 4.4 GB artifact，未完成核心源码审计。算法细节以所读 v1 为限；正式会议摘要报告约 8% 运行开销，v1 报告约 9%，之前交流中的 9% 指 v1，不能混用版本。
- FlowDist：核查 USENIX Security 2021 正文，及公开 GitHub 镜像中的图实现。原始项目在 Bitbucket；镜像 `14491152666feaf4a6b2c2f3f833e7c59b73dd57` 自述由原始 artifact 导入，本文不把镜像视作作者最新版本。未运行其默认管线或变体。
- MirrorTaint：核查 ICSE 2023 正文、官方仓库 `54fcbfc5bb3a0d7cd30309098355d999553a861b` 的指令规则、README 和文件清单。仓库提供 agent JAR；`Instrumenter` 目录主要用于适配比较工具，不能冒充 MirrorTaint 核心源码。未反编译或运行 agent。
- 我们：直接读取固定提交的 planner、采集器、字节解释器、请求分组和跨服务拼接代码。10 月 4 日主机结果沿用本对话中已经核验的归档，本次未重复采集。

**2. 三篇方法与我们的具体位置**

| 对照项 | 论文/公开实现的证据 | 当前实现与差距 |
| --- | --- | --- |
| HardTaint 的寄存器观测选择 | v1 §4.1 用值流图的连通关系和 must-value-set analysis 消除可推导的地址寄存器记录；不确定关系保留观测。[H1] | `gin_byte_adapter.plan_binary` 对 `main.transform` 解码后的每条指令调用 `add`，没有值流图冗余消除或 must-alias 分析。 |
| HardTaint 的控制流与循环优化 | v1 §4.1 使用支配关系减少基本块记录，按循环归纳变量依赖减少重复观测；§4.2 通过重写插入 PTWRITE。[H1] | 当前每次循环执行仍产生逐指令事件；只是范围已被人为限定，不能称为自动稀疏观测。 |
| FlowDist 的路径计算 | §3 / Algorithm 2 用方法事件激活静态依赖，再按覆盖裁剪，搜索进程内路径并连接跨进程片段；论文明确保留可能的伪依赖。[F1] | 我们对限定内存区建立实际写入定义，从最终 Writer 反向切片；范围较小，尚无大程序候选切片发现能力。 |
| FlowDist 的身份信息 | 公开镜像 `DynTransferGraph.java` 含覆盖裁剪、对象 ID 集合与按方法发生时刻裁剪的接口。[F2] | 不能把它描述为“完全没有对象身份”。默认管线是否使用这些接口、能否区分同一语句的多次写入，需运行验证。 |
| MirrorTaint 的字段身份 | 镜像堆/栈维护标签；官方指令表以对象与字段、数组与下标定位标签，并处理局部变量、参数与返回值。[M1][M2] | `ByteMachine.memory[address]` 保存当前定义，来源标签是读取编号与字节位置；只覆盖四字节、不重叠缓冲区，没有一般堆对象生命周期模型。 |
| MirrorTaint 的跨服务连接 | §IV-E 已将单服务输入输出关系与分布式 trace、边界数据标识关联后拼接。[M1] | OTel + 本地依赖图并非新组合。我们额外核对 span 父子关系、实际 header、收发正文和解码对象，但只支持当前固定 JSON/调用拓扑。 |

以上是方法差异，不是精度排名。尤其不能从 Java 工具不能直接运行 Go 二进制，推出其算法无法处理同值来源、覆盖或请求实例。

**3. 当前代码实际做了什么**

| 代码位置 | 已实现 | 不能据此宣称 |
| --- | --- | --- |
| `scripts/gin_byte_adapter.py:plan_binary` | 指定函数、边界和 Go ABI 后，从真实反汇编生成偏移，校验 ELF 指令字节；对已支持叶函数指令布点 | 任意二进制自动发现字段、自动找到最小观测集 |
| `scripts/go_byte_adapter.py:decode_function` | 有限指令集、函数内直接分支、一个返回；最多 64 条静态指令 | 任意优化编译代码、间接调用、完整指令集 |
| `scripts/gin_byte_capture.py:source` | 在目标 PID 内以 R14 的 G 地址管理请求作用域；过滤作用域外框架事件 | 跨 G 数据流已连接、过滤一定消除了探针命中成本 |
| `scripts/byte_provenance.py:ByteMachine` | 重放寄存器/字节读写；每次 store 更新内存当前位置的定义；保留逐步节点和来源集合 | 通用堆对象身份、任意别名、任意加工的语义解释 |
| `scripts/byte_provenance.py:infer` | 将三次已配置读取与工作函数参数绑定；检查实际事件、内存读取和输出一致性 | 自动寻找任意 source；动态决定从文件/数据库内部哪个历史版本读取 |
| `scripts/gin_byte_boundaries.py:group_events` | 用进程、G、作用域代次隔离事件；在现有执行范围支持线程迁移 | 在进程重启、对象释放后复用、跨请求缓存共享等情况下都能恢复对象生命周期 |
| `scripts/gin_cross_boundaries.py:bind_service/stitch` | 验证接收/解码/返回对象；将上游输出位置接到下游远程源位置，再反向切片 | 对 JSON 任意字段、键名、动态结构或其他协议都能自动映射 |
| `scripts/gin_otel_boundaries.py:span_chains/stitch_otel` | 验证当前单次同步调用拓扑及唯一上下文，并与实际探针 header 对照 | 自动支持扇出、重试、缓存、缺失 trace |

当前图能去掉完全覆盖后的上游来源，是因为每个目标字节的状态由最新写入替换，最终切片只保留可达定义。部分覆盖保留未被覆盖位置的来源。这不是比较值是否相同，而是跟踪定义与实际存储位置。

二进制构建仍固定 Go 1.25.4，并关闭内联。根函数调用序列、边界布局、JSON 形状均有固定契约。上游 A/C 选择在当前夹具中来自请求参数；观察到工作函数输入指针即可完成该选择的绑定，不等于整个业务分支都已被指令级跟踪。

`unknown` 表示已配置模型的一致性/完整性检查失败。它不是“任何未采到的隐蔽写入都能发现”的保证。特别是未知路径写入相同数值、且没有触发已检查边界变化时，当前机制没有普遍的发现证明。

已核验结果：24 次外部请求及 24 次上游调用，2992 条事件，99 个 span，32 条预期最终源关系全部正确；下游 21 个请求观察到线程迁移。该结果足以作为工程基线，不能当成真实应用精度或性能结论。

**4. 现在可以成立、不能成立的差异**

| 命题 | 判断 | 原因 |
| --- | --- | --- |
| 不为来源传播持久重写目标二进制 | 成立，是部署约束下的区别 | 使用外部 uprobe；但 OTel 接入涉及应用配置，运行时探针也不是无开销、完全被动的观察。 |
| 能处理当前 Go/Gin 请求迁移与固定 JSON 来源连接 | 已有实验支持 | 不应外推到一般 Go 堆或异构多语言系统。 |
| 比 FlowDist 更准确地区分所有运行时版本 | 未证明 | 需要同一来源语义、同一测试，并核实其对象身份选项。 |
| 比 MirrorTaint 更能区分同值数据 | 未证明 | 它已有字段/数组身份；其论文里的共享对象过度污染不能泛化到所有同值输入。 |
| 比 HardTaint 更省运行时成本 | 未证明 | 当前无对应性能评估；不能用不同硬件、不同负载和不同输出语义下的论文数字比大小。 |
| 减少探针仍保持来源准确性 | 尚未实现 | 当前核心要求逐条事件与重放的 PC 顺序匹配。 |
| “二进制 + eBPF + trace”本身是新算法 | 不成立 | 工具组合不足以证明方法上的新增能力。 |

直接部署的障碍也要与算法能力分开：HardTaint 的所读方案要求重写和相应 PT/PTWRITE 硬件；FlowDist、MirrorTaint 的已发布实现依赖 Java 分析/执行环境。它们不是当前 Go 目标的直接替换件，但这不意味着我们功能更完整。

**5. 一个必须加入的强基线：入口快照 + 模型重放**

不能只与“源码扫描 + 普通 trace”比较。当前叶函数的输入四字节已经完整采集、可执行指令有限、没有内部调用，输出区又与源区分离。在这些前提成立、所有后续读均由入口状态与已建模写入决定时，入口状态可以确定执行与依赖；逐指令事件主要增加一致性核验。

因此必须增加“边界快照 + 确定性解释器重放”的基线，并明确它的前提。它若已经解决冻结的三组实验，就不能把三组结果归功于必须额外采集大量内部事件。对于可变对象、未知调用或并发写入，必须另行证明入口状态是否充分，不能默认可重放。

**6. 候选研究问题与正确性条件**

建议研究：在明确的程序/内存模型中，为输出字段自动选择足够的外部观测，使具体源读取实例与覆盖依赖可以唯一确定；在无法覆盖影响输出的状态变化时，报告未解决的依赖。

定义执行 e、输出字段 f、观测集合 P、实际源读取实例集合 S(e,f)。观测 O_P 包含保留的探针事件及已有调用上下文。一个用于讨论的充分性条件是：

`对于模型允许的 e1、e2，若 O_P(e1) = O_P(e2)，则 S(e1,f) = S(e2,f)。`

这是我们需要建立和检验的条件，不是已经证明的定理，也不声称该形式本身新颖。若目标还包括传播路径或写入版本，右侧必须比较相应图或版本，而不能只比较最终源集合。

基本优化目标是降低观测成本，同时满足上述条件。成本应按动态命中次数、每次导出字节、内核/用户态处理成本衡量，不应只统计静态探针数量。入口值、地址推导、分支结果和库摘要有可能减少观测；会影响来源身份的未知写入、调用副作用和内存复用不能只凭数值没变就省掉。

对 HardTaint 的启发应采用“有条件推导，不能推导则保留观测”。借用优化时还要对齐标签语义：保留是否污点、保留多源集合、保留每次读取实例、保留完整历史图，是不同要求。不能把一个只保留较弱输出的配置当作完整溯源的等价基线，也不能在未审查证明条件时认定其优化会错。

**7. 最小验证设计与停止条件**

先不扩 Java、Rust 或第三个服务。先在现有 Go 分析范围内形成一个可复现的观测选择实验，再判断是否值得扩场景。

| 对照 | 作用 | 公平性条件 |
| --- | --- | --- |
| 静态分析 + 普通 OTel | 给出粗粒度候选；测试真实来源歧义是否存在 | 允许使用其实际拥有的请求参数和 span 属性，不故意隐藏显而易见的判定信息 |
| 边界快照 + 模型重放 | 检查内部观测到底新增了什么 | 输入、别名和外部写入假设全部公开；超出假设不能输出确定结论 |
| 当前逐指令采集 | 相同受限模型下的密集观测参考 | 仍需独立真值，不把旧实现的结果直接当 ground truth |
| 拟议的稀疏观测 | 检验事件减少是否保持来源关系 | 同一二进制、同一输入分布、同一输出语义；派生事件必须标明为推导，不能伪装成采集事件 |

建议用以下语义用例控制范围；超出现有解释器的用例先列为 unsupported，不能补手工答案冒充支持。

| 用例 | 要排除的错误解释 |
| --- | --- |
| 当前 assign / partial / overwrite | 保证优化不损坏已有来源与覆盖语义 |
| 两次执行都有相同分支覆盖，但循环中数据来源访问顺序不同 | 覆盖集合不等于每次写入顺序；需先确认基线有哪些对象/发生时刻信息 |
| 相同数值的不同读取实例进入同一输出存储位置 | 数值相同不能替代实例身份；源的判定单位需固定为读取实例 |
| 同一 trace 中重复调用同一接口，输出相同 | 需要调用实例与数据位置对应；当前拓扑会拒绝，必须先明确扩展范围 |
| 未知调用写入已跟踪对象，或者观测缺失 | 已识别的模型缺口应导致 unresolved；隐藏同值写入需检查观测充分性，不能仅检查末值 |

各个用例不预设三篇论文一定失败。若要评估原工具，先构造其支持环境中的同语义版本；Java 版本只能用于能力对照，不可直接拿其耗时与不同语言的 Go 版本排名。若实现论文启发的消融版本，必须注明“我们实现的近似基线”，不能冠以原工具名称。

报告至少包括：来源关系 precision/recall、完整正确的请求比例、unknown 比例、支持范围覆盖率、动态事件数与导出字节、吞吐和 p95/p99 延迟、采集与分析各端 CPU/内存、离线分析时间，以及依赖配置的适配工作量。所有请求都进入统计；不能只在 resolved 子集算漂亮的准确率。采样重复与不确定区间用于控制性能噪声，不把一次成功视为稳定成本。

停止条件：

1. 稀疏结果与独立真值一致，已有三组回归保持正确。
2. 至少确认一类边界信息确实不足、而额外观测能够区分的执行；若没有，先缩减方法，不继续加探针。
3. 事件减少确实转化为可测成本收益；若只有静态点数减少，不能宣布轻量。
4. 未解决情况被计入覆盖率，且支持边界可重复判定。

满足这些条件后，再进入一个真实 Go 应用的字段场景。若边界重放已足够或 eBPF 代价不合适，应据结果调整方案，而不是人为挑选让基线失败的条件。
