## 首次主机加载失败与修复（2026-10-03）

包 `json-output-provenance-20261003-153618-047a.zip` 的程序编译成功，但 verifier 报 `R2 min value is negative`，拒绝加载 `json_format_exit`。错误外层的 `Permission denied` 不表示缺少 sudo；这里是探针程序未通过内核安全检查。目标尚未恢复执行，收到 0 条事件，没有真实输出溯源结果。

日志中，对 C `int` 返回值的范围检查约束了符号扩展后的 R1，但传给内存读取 helper 的长度来自原始 AX 对应的 R2 加一，验证器仍认为它无安全上界。修复改用 `bpf_probe_read_user_str`，helper 上限为编译期常量 32；检查其返回长度包含 NUL、没有达到截断边界，并且等于格式化返回值加一。推断器仍核对完整 JSON 字节与模型一致。该 helper 到 NUL 即停止，不主动记录终止符之后的缓冲区内容；事件预先清零。

扩展 native 回调测试覆盖 C 返回寄存器高位非零、提前 NUL、未终止字符串、读取错误和越界返回，11 项定向测试通过。这不是 BPF verifier 实测，修正后的内核加载仍待重跑。对上传实际 ELF 重建计划及独立指令执行也通过；其中模拟的 500 条事件不能当成主机采集。详见 [首次主机诊断](json-output-host-20261003-attempt1.json)。

## 本轮实际追踪的内容

| 阶段 | 来源证据 | 输出 |
| --- | --- | --- |
| pread | 进入/返回事件、fd 身份、文件偏移、返回字节 | 读取实例及字节版本 |
| 计算 | 原有二进制指令与调用观测 | 输出字段的执行依赖图 |
| JSON 格式化 | `format_json` 入口的输入地址和值、返回长度与生成字节 | 数字字段 `$.value` 的字节范围及序列化版本 |
| stdout | `write` 入口的缓冲区地址/字节、退出返回值 | 实际被成功写入的 JSON 字段来源 |

入口 `format_json(char *buffer, const uint32_t *value)` 调用 `snprintf`。**我们为这个固定接口声明了 `json-u32-value-v1` 规则，没有分析 libc 或任意序列化器内部的全部指令。**规则支持无符号 32 位整数、固定键 `value`、无空格及换行结尾，缓冲区容量固定 32 字节。JSON 数字范围从偏移 9 开始，长度随数值变化；键、标点和换行是固定格式，不作为来源字段。推断要求返回长度、JSON 字节及尾部 NUL 与模型一致。

序列化边在图中明确标为 `serialization-summary`，成功输出边为 `accepted-write`，保留各自证据类型。不能把摘要边称为逐指令证明的 libc 传播历史。此规则的依赖粒度是整个 uint32 到完整数字字段，不声称逐位数字的最小依赖。

绑定必须同时满足地址、操作顺序、执行身份和当前版本条件，再用值/字节检查一致性。相同数值或相同 JSON 文本不能替代地址和版本身份。一次格式化尚未写出就被下一次格式化覆盖时，只连接后一次版本。成功 `write` 的含义是内核接受了 stdout 的这些字节；运行器将 stdout 重定向到采集包的文件，并核对 FD 身份及最终文件内容，不代表网络远端已收到。

## 场景与独立真值

保留 C 读取的九类情形、两个偏移轮次：同值异源、两来源合并、覆盖、文件偏移变化、失败读取、EOF、常量回退、同位置重复读取等；追加：

- 先计算源数据，再通过已观测计算根函数用常量覆盖，最后输出不应保留旧来源。
- 两次序列化复用同一缓冲区，生成完全相同的 JSON 字节，但分别来自 a.bin 和 b.bin；只写出第二个版本，来源应为 b.bin。
- `write(-1, ...)` 返回 EBADF：保留写入尝试和缓冲区来源，但不生成已输出字段关系。
- 输出 0 与 UINT32_MAX，验证十进制长度和无符号转换。

共 **25 次计算、42 次读取尝试、24 次格式化、23 次写入尝试、22 条成功输出的 JSON**。36 次读取返回 4 字节，4 次 EBADF，2 次 EOF。真值由夹具独立记录，并在观测范围外输出；只在评分阶段使用。业务 JSON 本身不包含追踪标签、来源编号或正确答案。

评分同时检查计算字段来源、读取操作来源、已输出 JSON 字段来源、写入成功/失败、操作数量，以及由成功写入事件重建的完整 stdout 是否等于实际 stdout 和独立预期。不会把“曾经计算/格式化过”计成“已经输出”。

## 本地验证

新增 11 项测试全部通过。原生 GCC 编译的程序真实执行 pread、snprintf 和 write，生成独立 stderr 真值及 stdout；另一条 Python 真实 pread + Unicorn 计算指令执行路径生成观测事件，格式化测试字节用 Python JSON 库构造。推断和评分通过，已输出来源关系 TP=21/FP=0/FN=0；22 个输出字段中的常量没有外部来源，合并字段有两个来源，关系数不等于字段数。

这些测试事件是独立构造的，**不是内核采集**。此外，将实际生成的格式化/写入回调 C 代码放入 native C++ 测试壳，检查参数、负 fd/返回值、内存读取错误、非法长度和范围过滤；测试壳使用与 BCC 一致的普通 tracepoint `args` 参数，但模拟了 maps/helpers，不能代替 BPF verifier。

完整套件 143 项：135 项通过、5 项因为无本地 Go 编译器跳过、3 项既有 HTTP 测试被 socket 权限阻止。旧 C/Go 读取入口的 BPF 生成源码与已通过的主机包保持一致。记录见 [本地验证报告](json-output-local-validation.json)。本轮未重复声称十个旧包都做过完整回归。

## 明确的范围

- 单线程；由已观测的计算根函数独占写入结果字段，由指定格式化函数独占写入 JSON 缓冲区。格式化/写入期间无其他线程修改数据，交接期间无未观测写入。
- 本轮记录当前计算输出版本与序列化缓冲区版本，没有实现通用对象生命周期、任意地址重用或全程序写入监控。未观测的同值覆盖无法只凭值比较识别，违反独占写入前提的程序不能直接套用本模型。
- 只支持固定 `{"value":uint32}`，不支持字符串转义、嵌套对象、浮点数、任意 `printf`/JSON 库。
- 部分写入、序列化截断、未知 fd、缺事件、内存快照错误等拒绝给出完整来源结论；没有实现分块重试的 JSON 重组。写入失败或零字节返回不会产生已输出来源关系。
- 没有把 stderr 中的真值当作业务 sink，没有接入 Go JSON、网络发送或跨服务传播。

共用入口仅新增可选的 oracle loader，旧入口继续按原方式读取其 stdout 真值；C/Go 读取推断核心没有修改。新增 `json_output_boundaries.py` 放置 JSON 规则与输出来源绑定，C ABI 和探针挂接保留在 `json_output_provenance.py`，为后续语言适配留出边界。
