# Gin 并发请求的来源状态隔离

## 目标与当前状态

本轮把已通过主机验证的串行 Gin 场景扩展为 **每批 4 个并发请求，7 批共 28 个请求**。每个请求内仍使用 `runtime.LockOSThread`，暂不处理请求内线程迁移、子 goroutine 传播或共享可变业务对象。

**2026-10-03 用户 WSL2 主机的真实 Go 1.25.4 / Gin 1.11.0 / BCC 0.29.1 并发采集已通过。**从 892 条原始事件独立重建，全部推断与评估结果一致；28 个请求、36 次计算、56 次读取，输出来源关系 TP=28/FP=0/FN=0，全部客户端正文匹配。报告丢失、提交、状态和内存读取错误均为 0。见 [主机核验记录](gin-concurrent-host-20261003.json)。这些正确率仅代表本轮受控夹具。

7 批均观测到 4 个不同线程、4 个不同 G 地址的请求范围实际重叠；按时间戳核对的共同重叠区间均为正。全程有 8 个 TID、14 个 G 地址，6 个 TID 被后续请求复用，各请求的读取和根调用计数正确重新开始。19 个客户端 ticket 与采集请求实例号不同，仍正确匹配来源位置及正文。`request_switches=418` 仅指按全局编号排列的相邻事件切换请求归属，不是操作系统上下文切换次数，也不能用来推导性能。

二进制、夹具及框架源码哈希、静态探针计划和生成的采集器源码均已核查。此前本地 C++ shim、Unicorn 与实际 HTTP 测试提供独立检查；旧串行包的 446 条事件完整回放一致，其 BPF 源码保持一致。

## 运行

本轮已通过，无需再次运行。复现仍使用 Go 1.25.4、BCC 与系统 Python，无需 Docker：

```bash
git pull --ff-only origin main
sudo env "PATH=$PATH" GOPROXY=https://goproxy.cn,direct \
  /usr/bin/python3 scripts/gin_concurrent_provenance.py run
```

脚本自动发送请求并生成 `artifacts/gin-concurrent-provenance-*.zip`。成功或失败均返回整个 ZIP。旧串行场景不需要重跑。

## 这次具体改变了什么

业务计算函数、普通响应结构体和 `c.JSON` 保持相同语义。取消业务请求外围的串行互斥，为每个请求单独分配输入和输出对象。文件描述符仍共享，因为文件不可变且使用带显式偏移的 pread；输入内存缓冲区不共享。

每批四个请求在三处汇合：第一次读取后、第二次读取后、业务计算后。这是测试调度夹具，保证采集中能看见请求范围重叠和阶段交错，不用于推断数据来源。评估要求所有 7 批满足阶段顺序、范围重叠，并观察到 4 个同时活动的请求范围；把串行事件喂给评估不能冒充并发通过。

模式仍覆盖 left、right、merge、overwrite、same、zero、max，重复四组。每个请求在 a.bin/b.bin 中使用自己的 16 字节区域，区域内容相同。这可以检查“JSON 数值正确，但来源被串到另一请求的读取位置”的错误。预期 28 个请求、36 次计算根调用、56 次读取，以及 28 个最终输出到文件读取范围的来源关系。

## 采集状态与执行身份

- 请求进入时分配原子的 64 位请求实例号。当前进程内，每个活动的固定线程映射到独立请求上下文；线程/G 地址本身不是请求实例号。
- 原来的单份读取状态改为请求上下文中的独立状态：未完成读取、读取编号、G 地址和请求内观测序号分别保存。机器调用状态仍复用共用采集器的线程映射，并在请求边界检查、重置和清理。
- 全局观测编号原子递增，用于检查重复与缺失；每个请求另有连续观测编号，用于检查归属和完整性。编号不解释为跨线程数据因果边。
- 按全局编号整理 perf buffer 的跨 CPU 交付顺序，再按请求实例分组；只要求请求内部时间戳单调，不要求不同 CPU 的时间戳采样顺序与全局编号严格一致。
- 请求退出后删除活动上下文和调用状态。后续复用同一个 TID/G 地址时必须得到新的请求实例号，读取编号和根调用计数重新开始。
- 请求范围内的 TID/G 变化、重复活动身份、缺少边界、序号不连续、存储失败和实际丢事件不能通过验证。当前映射容量为 64 个活动上下文，本轮只验证 4 个并发。

## 请求与客户端如何匹配

并发时不能把第 N 个进入、发出或完成的请求当成同一个请求，也不能用相同 JSON 值配对。

客户端为测试请求使用 `ticket` 查询参数；服务器在观测范围结束后单独记录 ticket、mode 与该请求私有输入对象的地址，并保留对象到测试结束，避免评估期间地址重用。这份记录是**仅用于评估的身份对应表**，不是字段传播标签，也不参与算法推断。

采集和推断从真实读取与计算事件获得输入对象地址，独立重建请求来源。推断完成后，评估才用对应表把结果连接到正确的客户端请求，检查预期来源、文件偏移及实际正文。推断不读取 ticket、mode、对应表或客户端正文。实际请求实例号可以与 ticket 完全不同。

这是本次受控实验的正确性检查方法，不是一般生产 HTTP 流量与请求身份自动关联的完整方案。

## 重建核心复用与范围

并发适配层先校验和拆分请求，再调用同一份文件读取、机器指令和 JSON 摘要重建逻辑。串行入口保留原默认行为。检查同时活动请求的输入/输出对象范围不能重叠；共享可变内存依赖不在本轮支持范围内。

JSON 仍限定固定 `balance` uint32 字段，序列化使用已审计结构体的显式摘要。输出终点仍为 Gin 响应写入成功，客户端正文另行核对；没有新增 socket 字节级血缘或一般 JSON 支持。本次仍禁用编译内联。

## 验证方法

1. 真实编译的 Go 业务指令用 Unicorn 独立执行，构造 4 路交错事件。测试故意让请求实例号、客户端 ticket、入口顺序和完成顺序不同。
2. 扰乱 perf 交付顺序、设置跨 CPU 时间戳交错，要求重建结果不变。
3. 破坏请求号、G/TID、局部序号、边界、来源文件偏移、客户端对应表或采集统计，要求推断或评估失败。
4. 构造同值不同请求偏移、重用线程身份、共享活动输入对象，以及串行假冒并发等反例。
5. 原生 C++ shim 执行生成的完整采集器源代码，模拟两个请求同时持有未完成读取和调用栈，核对状态隔离、清理、身份重用及更新失败。BPF maps/helpers 是模拟实现，该检查本身不能证明内核采集成功。
6. 启动真实 Gin 服务并发送 28 次并发 HTTP 请求，检查每个正文与独立预期及评估对应表。
7. 重放之前已通过的串行主机包，核查源码生成、全部推断和评估结果一致。
8. 核查本轮真实主机包的源码与二进制哈希，重建全部计划并从原始事件重放推断和评估；逐批核查真实范围重叠，逐请求核查身份、连续序号、状态重置、同值换源、常量覆盖和客户端正文。

详见 [本地验证记录](gin-concurrent-local-validation.json)。复现本地测试需要 Unicorn、g++ 和 loopback socket 权限：

```bash
python3 scripts/gin_concurrent_provenance.py build --out "$PWD/artifacts/gin-concurrent-test-build"
GIN_CONCURRENT_BUILD="$PWD/artifacts/gin-concurrent-test-build" \
  python3 -m unittest discover -s tests -p test_gin_concurrent_provenance.py -v
```
