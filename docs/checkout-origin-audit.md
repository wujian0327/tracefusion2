## 结论

选择 Online Boutique `checkoutservice.prepOrderItems`，固定官方发布 **v0.10.4 / 474d0f2eb73d97525234995a40d7781b7923a07d**，Go 1.25.4。应用函数保持原样，测试增加的本地 gRPC 对端和客户端拦截器只提供独立检查证据。

这个函数适合作为下一阶段的真实业务落点，但**本轮没有发现或证明强基线无法解决的问题**。正常成功路径上的关联很规则，普通字段敏感分析、调用摘要和有界运行时对象关联都是应当允许的基线能力。不能把新增对象、切片和 RPC 适配工作称为新的溯源算法。

已完成：两个真实二进制构建、三个函数的机器码结构检查、六个原函数测试用例。未执行：TraceFusion 对此函数的 eBPF 溯源、HardTaint 等论文原系统、完整商店部署、性能基准或安全漏洞复现。详细结果见 [本地记录](checkout-origin-audit-local.json)。

## 为什么选这里

原函数接收购物车条目切片。对每一项依次查询商品，调用币种转换，再将原购物车对象与转换返回对象放入订单条目。包含真实动态长度循环、堆对象、生成的 protobuf 访问器和两个 gRPC 调用，但不需要首先部署支付、邮箱、购物车数据库等全部组件。

本轮边界为 `prepOrderItems` 的入口和返回，重点查询 `out[i].Item` 与 `out[i].Cost`。父函数 `PlaceOrder` 的总价计算和完整订单输出只做源码/机器码审计，没有运行支付或发送邮件。原版本依赖固定后可直接使用已有 Go 工具链；未为编译方便改写官方依赖或业务函数。

## 输出究竟能追到哪里

| 查询 | 源码可以确定的关系 | 运行时需绑定的实例 | 此处不能直接声称的能力 |
| --- | --- | --- | --- |
| `out[i].Item` 及其字段 | 将本轮 `items[i]` 对象引用放入结果 | 本次函数调用、实际切片与元素对象 | 单凭商品 ID/数值相等区分多次读取 |
| `out[i].Cost` 及其字段 | 将本轮币种转换返回对象放入结果 | 具体 Convert 调用及其返回对象 | 币种服务内部实际依赖了哪些数据 |
| 币种调用的 `From` 参数 | 使用本轮商品返回对象的 `PriceUsd` | 本轮 GetProduct 返回与 Convert 请求的对象关联 | 调用顺序本身就证明汇率加工的字段依赖 |

在此函数内，可以追到**某次 RPC 返回字段**。如果继续追到商品价格及汇率，就必须分析/观测币种服务内部，或使用已经验证的服务摘要。本轮模拟汇率服务的运算规则只是测试真值，不是系统自动推导出的官方 CurrencyService 摘要。

商品 ID 影响查找哪个商品；是否将它列作价格的数据来源，取决于选择依赖/显式数据依赖的定义，不能混为一种边。本轮仍采用既有显式来源口径，不据此扩成隐式信息流分析。

## 实际编译结果

下面是函数自身的**静态**指令及调用站点数，不是执行事件数、动态成本或完整传递调用图。

| 函数 | 默认优化：指令 / CALL | 关闭内联：指令 / CALL |
| --- | ---: | ---: |
| `prepOrderItems` | 196 / 13 | 177 / 18 |
| `convertCurrency` | 73 / 5 | 79 / 7 |
| `PlaceOrder` | 565 / 39 | 561 / 40 |

`prepOrderItems` 有切片/对象分配、GC 写屏障、RPC 和错误构造。关闭内联后还出现接口间接调用；默认优化消掉了部分访问器调用。这说明不能把“关闭内联”简单理解成机器码一定更容易分析。

当前叶函数解码器对三个函数的首个拒绝原因都是 `Leaf function outside instruction budget`。即便提高 64 条指令限制，当前固定四字节区域、参数 ABI、无调用叶函数和封闭内存模型也不适用。

**这是我们原型的实现范围限制。**本轮没有据此认定 HardTaint、通用符号执行或字段敏感静态分析不支持这些函数，也没有测得路径爆炸。这里正常循环可用逐项关系表达，没有必要预设枚举所有路径才是强基线。

## 原函数运行检查

使用两个本地模拟 gRPC 服务角色（同一测试服务器上注册 ProductCatalog 与 Currency），运行官方原函数。测试设置 OTel provider 与 TraceContext 传播器，不调用生产 `main()`；客户端拦截器记录返回对象用于真值核对。因此，这些结果不能宣传成外部 eBPF 采集结果。

| 用例 | 输入条目 | 返回条目 | 商品 RPC | 币种 RPC |
| --- | ---: | ---: | ---: | ---: |
| 空输入 | 0 | 0 | 0 | 0 |
| 单项 | 1 | 1 | 1 | 1 |
| 相同内容的不同实例 | 8 | 8 | 8 | 8 |
| 相同内容的不同实例 | 32 | 32 | 32 | 32 |
| 第二次商品查询失败 | 4 | 0，返回错误 | 2 | 1 |
| 第二次币种转换失败 | 4 | 0，返回错误 | 2 | 2 |

成功用例共 41 个订单条目，检查了 123 个对象关系：输出条目与输入对象、输出 Cost 与转换返回对象、转换 From 与商品 PriceUsd 的引用关系。重复商品 ID 和相同数值没有被当作同一个 RPC 实例。错误用例确认途中构建的部分订单没有作为正常结果返回。

这些结果支持“该函数具有可表达的边界字段关系”，不证明这些关系已经被二进制分析自动提取，也不证明这些观测在一般情况下最少。

## 一个实际的 trace 上下文问题

固定版本的 `convertCurrency` 使用 `Convert(context.TODO(), ...)`，没有传递传入的 `ctx`。在配置好 OTel 传播器的测试夹具中，45 次商品 RPC 都延续了调用根 trace，而 44 次币种 RPC 都没有延续该根 trace。

这是一个已通过运行验证的上下文传递问题，不是字段来源算法创新，也不应故意保留它来打败普通 trace 基线。若后续比较，必须允许修复上下文或提供等价调用关联证据。生产初始化配置与完整部署的 trace 质量未在本次测试中评估。

## 现在能够缩小到什么问题

真正值得核查的候选是：**从真实编译产物自动提取有限范围的字段传递关系，并用运行时对象/调用实例绑定这些关系，需要多少额外观测？**

但字段敏感分析、函数摘要、堆对象身份和 RPC 边界关联都已有研究，不能把它们重新组合就宣布创新。这个函数可以作为检查自动化程度的试验点：

1. 分析器不能读取测试中的手工来源答案，应自动得到输入元素、RPC 返回和输出元素之间的关系。
2. 基线应允许普通字段敏感摘要、对象关联与正确的 trace 上下文，不能故意要求它逐指令记录。
3. 只记录源头时，明确停在 RPC 返回字段；跨越远端加工则补齐远端证据。
4. 若普通摘要方法已能自动获得相同结果与成本，停止在这个函数上继续包装“省采集创新”。

本轮推荐保留此函数作为真实集成对象，暂不增加更多编程语言、更多安全情节或新一轮微型分支规则。下一次推进应先验证自动摘要是否存在具体障碍，而不是先写一个为该函数手工配置的成功演示。
