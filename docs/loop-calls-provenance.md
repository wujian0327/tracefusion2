本轮 Go 未进入慢路径，原始命中与提交均为 1276，首次抢占现象未复现。这验证了本次受控启动及快路径实验；不能由一次成功推导任意负载下无丢失、一般抢占/扩栈支持或低开销。旧包缺少 errno，重跑成功也不会反向证明旧提交失败的具体错误码。

| 收到事件 / 提交失败 | 639 / 301 | 812 / 466 |

两包均满足 `attempted_events = received_events + submit_errors`。`lost_events=0` 不能说明没有丢失：perf 提交失败已单独计数。收到的输入、输出、栈及 Go guard 读取均无错误。缺失调用和慢路径仍然让整体评分失败，当前召回率不能脱离采集缺失解读成算法准确率。

提交失败集中在毫秒级突发期间，原采集器每 CPU 仅 64 页 perf 缓冲，回调还逐事件 flush 文件，怀疑消费者排空速度不足。旧包没有记录失败 errno，不能仅凭包内容断言所有失败都是 ENOSPC。修复将缓冲改为 **每 CPU 1024 页**（4 KiB 页时为 4 MiB），去掉逐事件 flush，退出后显式 flush/fsync，继续排空尾部事件。`capture.json` 记录实际缓冲页数/字节数；跨函数 BPF 新增 `submit_error_errnos` 计数，以便复现时确认具体错误。没有降低事件量、过滤失败调用或放松评分条件。

Go 第一条事件的 guard 为 `0xfffffffffffffade`，等于 Go 1.25.4 的 `stackPreempt`（`uintptrMask & -1314`，见 [官方源码](https://github.com/golang/go/blob/go1.25.4/src/runtime/stack.go)）。因此确认是运行时抢占慢路径，不能声称已支持该路径。夹具现在于 SIGSTOP 恢复后、进入目标函数前调用一次 `runtime.Gosched()`，让挂接等待期间挂起的调度请求有机会在观测范围外处理。仍保留 `LockOSThread`、正常栈保护和观测范围内的慢路径拒绝；这不是一般抢占/扩栈支持，也不保证后续不会再次抢占。

另对两个包内的真实二进制分别用 Unicorn 独立执行：C 940 条模拟事件、Go 1276 条模拟事件，各 24 次调用均通过字段/值/helper 次数检查。Go 使用合成正常栈 guard，不模拟运行时调度；因此该结果证明此次真实 Go 编译输出在限定快路径下可重建，不能替代重新采集。

修复后新增 3 项模拟 BCC 传输测试通过，覆盖恢复前打开缓冲、退出后尾部事件持久化和错误计数保留。完整套件 113 项：106 项通过、4 项因缺少 Go 编译器跳过、3 项旧 HTTP 测试因环境禁止 socket 而报错。新 BPF errno map 及 Go 启动变更已在上述重跑中执行；本轮无提交错误，非零 errno 分支仍仅由模拟测试检查。

## 场景和独立真值

每种语言各 3 个根函数，分别运行 0、1、2、4 次迭代、两个数值轮次，共 24 次根调用。两个源字段故意同值。helper 在前两轮读取敏感字段，后续读取公共字段。

| 场景 | 行为 | 四次迭代的预期 |
| --- | --- | --- |
| 覆盖 | 每轮调用读取 helper，覆盖结果 | 只保留最后一轮的公共字段来源；4 次 helper 调用 |
| 累积 | 每轮调用读取 helper，再相加 | 保留敏感和公共字段来源；4 次 helper 调用 |
| 嵌套加工 | 每轮调用加工 helper，它再调用读取 helper，XOR 后返回累积 | 保留两种来源；8 次 helper 调用、最大深度 3 |

零次覆盖输出 42，零次累积及加工输出 0；均没有输入字段读取贡献。主程序独立计算输出、字段来源和 helper 次数；推断不读取真值。正式评分包括这些量以及多轮执行的向后边证据。机器读取实例和依赖图也会输出，但没有将源码迭代编号当作编译后读取编号，也没有宣称已测量所有图边的精确率/召回率。

## 共用算法

1. 从二进制发现根函数及可达直接调用，允许函数内部 CFG 有环，要求函数调用图无环。对范围内所有指令设置观测点，不枚举所有循环路径。
2. 按事件顺序检查寄存器、标志位、输入输出内存、栈和 CFG 转移。机器模型核查真实返回地址，逻辑调用栈核查函数、位置和深度，两者必须一致。
3. 每次执行 CALL 新建 `call1`、`call2` 等实例，记录父实例、调用位置、进入及返回序号。同一静态调用位置执行四次会产生四个实例，不按函数名合并。
4. 指令节点按根调用、动态调用实例和执行序号区分。复用 `interproc_model.py` 的参数、返回值及读写版本传播，再调用 `loop_provenance.reconstruct` 反向提取贡献来源。覆盖消除旧贡献，累积保留参与运算的贡献。

`call_instances` 展示调用父子关系；`source_reads` / `contributing_reads` 将机器读取与 `call_instance` 绑定。编号仅在当前根调用内有意义，不是跨请求的全局字段标签。C 与 Go 没有各写一套循环/调用来源规则。

编译器可能把零值循环次数参数直接写入输出，代替写入常量 0。新引擎对此显式输出 `argument_sources: ["arg.select"]`，图中保留参数依赖；`sources` 仍专门报告输入字段。`arg.select` 是既有三参数边界模型对第三个标量参数的名称，在本场景中表示循环次数。不会将参数依赖静默丢弃，也不会伪称出现输入字段读取。旧单函数入口默认仍拒绝不在其范围内的边界来源。

## 当前边界

- Linux amd64、固定连续 uint32 字段、输入只读、既有有限指令集；只支持可解析的直接调用。
- 每次根调用最多 4096 条执行事件、调用深度最多 8、计划最多 32 个函数；有限栈快照沿用既有模型。
- 拒绝递归、间接/未知调用、调用配置中的其他根函数，以及回到函数入口探针的循环。尾调用不在本轮支持范围内，C 夹具关闭尾调用优化。
- C 只接受单线程执行身份；Go 只接受一个固定 OS 线程上的用户 goroutine，保留栈保护，观测到扩栈/抢占慢路径即拒绝，不支持栈迁移。
- 尚未覆盖一般堆对象、字符串/切片、并发共享状态、异常展开、跨服务或数据库内部血缘。
- 所有范围内指令均挂探针，尚未证明低开销；依赖为显式数据依赖，没有加入一般隐式控制流污点。
